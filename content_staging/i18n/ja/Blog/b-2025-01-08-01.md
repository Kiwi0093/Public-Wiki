# はじめに

`qemu` をアップデートしたところ、従来の WSL カーネルに TC（Traffic Control）のモジュールサポートが不足していることが判明し、そこから Linux カーネルを自分でコンパイルするという茨の道へ足を踏み入れることになりました……。

<!--truncate-->

# 経緯

実際のところ、経緯は「はじめに」で書いた通りです（じゃあ他に何の無駄話をするんだ？という話ですが）。
いくつかの補足事項は以下の通りです。

* 私の WSL は`会社`の Windows 上で動いており、Local Administrator 権限が回収されてしまいました。さらに開発部門（RD）ではないため権限の再取得は絶望的で、`wsl --update` による WSL のバージョンアップができません。
* もっとも、仮に `wsl --update` が使えたとしても、GitHub 上の WSL-Kernel ソースのデフォルト config を確認したところ、TC や QoS のカーネルサポートは含まれていませんでした……（つまり上の項目は……ええ、単に権限がないことへの愚痴です……）。
* WSL のカーネルにはモジュールを動的ロードする機能がありません（つまり `modprobe` コマンドが WSL では何の役にも立たないということです）。そのため、TC/QoS を後から動的に読み込む方法が使えません。

というわけで……このおっさんは自分のニーズを満たすため、自分でカーネルを config/compile する羽目になったのです。

# 感想

はるか昔、`Gentoo` を使っていた頃に Linux カーネルを config/compile したことがありました（`Gentoo` を使っていて自分でビルドしないわけにはいきませんからね）。ただ、それ以降は二度と自分で手を動かそうとは思わなくなっていました（昔はマメに `FreeBSD` のカーネルまで自分で config/compile していたのに、今では generic を使うようになったのと同じです）。

今回の作業は、正直なところ難しそうに見えて、実際やってみるとそうでもありませんでした……。
ただ、WSL で使うカーネルには基本的に「使うもの」と「使わないもの」の区別しかなく、使うものはすべて built-in にしなければならず module にはできない、という点に慣れる必要があります。これは初期の `FreeBSD` カーネルと基本的には同じ考え方であり、現在の `Linux` 主流カーネルの運用スタイルとはロジックが異なります。

また、こうした前提のもとでは、特定の目的で確実に必要な機能（今回なら `TC/QoS` や、私がよく使う `wireguard` サポートなど）以外に、どのモジュールが WSL に必須なのかを自力で記憶しておくのが難しいという点があります。そのため、どの解説でも推奨されているのは以下のコマンドを使う方法です。

`zcat /proc/config.gz > .config`

あるいは

`cat /proc/config.gz | gunzip > .config`

現在正常に動作している WSL カーネルの config を取り出してデフォルトとし、そこにアドオンのような形で必要な項目だけを足していく、というやり方です。この方法のおかげで、頭を悩ませる部分がかなり簡略化されました。

最後に……すべてが正常に動く WSL はやはり快適です。特に会社で「給料泥棒」をしている身として、消すことのできない`会社の Windows`に向き合わなければならないとき、WSL は私たち労働者の救世主なのです……。
