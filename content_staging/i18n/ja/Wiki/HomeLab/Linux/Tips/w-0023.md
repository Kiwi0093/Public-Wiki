## 一、 症状の整理：ログイン後の長いブラックスクリーンとゴーストウィンドウ

使用している Linux ディストリビューション（Arch、Fedora、Ubuntu、あるいは openSUSE など）を問わず、デスクトップ環境が **KDE Plasma 5 または Plasma 6** であれば、システムアップデートや GPU ドライバの変更、あるいは異常終了などを経た後、以下のような典型的なデスクトップ不具合に遭遇することがあります。

1. **ログイン後の長いブラックスクリーン待機**：SDDM や GDM でパスワードを入力した後、画面が 10〜30 秒ほど真っ暗なまま固まります。マウスカーソルは動くものの、デスクトップウィジェットやパネルがなかなか表示されません。
2. **過去のウィンドウが強制的に復元される**：システム設定ですでに「空のセッションで起動する（Start with an empty session）」にチェックを入れているにもかかわらず、起動のたびに前回終了前に動いていたターミナルやブラウザ、特定アプリがすべて強制復元されます。
3. **パネル（Panel）の遅延読み込みまたは消失**：ブラックスクリーンが終わった後、パネルが数秒遅れて表示されたり、右クリックメニューにまったく反応しなくなったりします。

## 二、 原因分析：なぜ GUI 設定で復元をオフにしても効かないのか？

KDE Plasma は内部で `ksmserver` と `plasmashell` に依存してセッションを管理しています。システムがクラッシュしたり、ディスプレイサーバー（X11/Wayland）が再起動したり、ドライバのコンテキストに異常が起きたりすると、下層でウィンドウのジオメトリ状態や GPU コンテキストを記録する状態ファイルが**破損した状態で書き込まれたり、読み取り専用としてロックされたりする**ことがあります。

これにより、次の 2 つの連鎖反応が引き起こされます。

- **GUI スイッチの形骸化**：システム設定画面上は「空のセッション」と表示されていても、バックグラウンドのデーモンが破損した古いセッションファイルを強制的に読み込んでしまいます。
- **20 秒タイムアウト保護機構の発動**：`plasmashell` が起動時にバックグラウンドで無効な GPU リソースを含む古いウィンドウを再構築しようと暴走し続け、Session Manager の接続タイムアウト（Timeout）保護機構が発動して初めて、デスクトップ要素がようやく遅れて読み込まれます。

## 三、 強制リセット：破損したセッションとキャッシュを削除する

GUI 設定が機能しない以上、最も直接的で効果的な手法はターミナルからコマンドを実行し、破損した状態ファイルとデスクトップコンポジタのキャッシュを完全に消去することです。

1. **セッション復元状態ファイルの消去**

   Plasma のバージョンによって設定ファイルのパスが若干異なるため、以下のコマンドで新旧両方の仕様のセッション記録をまとめて削除します。

   ```bash
   # Plasma 6 のセッション復元状態ファイルを削除
   rm -f ~/.local/state/plasmasessionrestorestaterc

   # Plasma 5 / 6 の旧版セッションディレクトリを削除
   rm -rf ~/.config/session/*
   ```

2. **デスクトップ要素およびウィンドウマネージャのキャッシュを消去**

   破損した QML キャッシュや KWin エフェクトのキャッシュも読み込み速度を低下させます。

   ```bash
   # plasmashell と kwin の一時ファイルを削除
   rm -rf ~/.cache/plasmashell*
   rm -rf ~/.cache/kwin*
   rm -rf ~/.cache/plasma*
   ```

3. **再起動して確認**

   上記のクリーンアップを実行した後、PC を再起動するかログアウトします。

   ```bash
   systemctl reboot
   ```

   _確認の目安：SDDM でパスワードを入力してから 1〜3 秒以内に壁紙とパネルが瞬時に読み込まれ、前回の残留ウィンドウが一切表示されなくなれば正常です。_

## 四、 高度な切り分け：それでも重い場合は Systemd ユーザーサービスを確認

キャッシュを削除してもなお遅延が発生する場合、高い確率で Plasma の起動に追従するバックグラウンドのユーザーサービス（Systemd User Services）に原因があります。

```bash
# 起動時に処理時間を要しているユーザーレベルのサービスを確認
systemd-analyze --user blame
```

特定のカスタムスクリプトやサードパーティ製同期ツール（クラウド同期ソフトや IME デーモンなど）の所要時間が異常に長い場合は、まず `systemctl --user disable <サービス名>` で無効化して切り分けてみてください。
