# WSL2 カスタム Linux Kernel ビルド・差し替えガイド

> <img src='https://img.shields.io/badge/Status-Active-A8FF24?style=for-the-badge&labelWidth=100' height='38' />

![WSL](https://img.shields.io/badge/WSL-Supported-green?style=plastic&logo=linux)

:::tip
WSL では、デフォルトでユーザーがカスタム Linux Kernel（カーネル）を読み込むことが許可されています。特定の高度な用途（例：QEMU/KVM 仮想マシンを実行する際にブリッジネットワークや高度なトラフィック制御を使用する場合など）では、公式のデフォルトカーネルに必要なモジュール（TC/QoS など）が不足していることがあります。自分で設定・ビルドした WSL カーネルを使うことで、こうした必要な機能を補うことができます。
:::

## 一、 ビルドの事前準備 (Preparation)

### 1. ビルドに必要なパッケージのインストール

Arch Linux (WSL) 環境では、基本的な `base-devel` に加えて、カーネルのビルドに `ncurses`（`menuconfig` 用）、`bc`、`flex`、`bison`、`pahole`、`libelf` などのツールが必要です：

```bash
sudo pacman -S base-devel ncurses bc flex bison pahole libelf
```

### 2. WSL2 Linux Kernel ソースコードの取得

Git を使って Microsoft がオープンソースで公開している WSL カーネルのソースコードを取得します。

> **ヒント：** ここでは例として `6.1.y` 系を取得しています。別のバージョンを使いたい場合は、GitHub リポジトリ上のブランチ名に合わせて置き換えてください。`--depth=1` を付けると最新のコミットのみを取得できるため、ダウンロード時間とディスク容量を大幅に節約できます。

```bash
git clone https://github.com/microsoft/WSL2-Linux-Kernel.git --depth=1 -b linux-msft-wsl-6.1.y
cd WSL2-Linux-Kernel
```

> [!info] Updated 2026-11-27
> 近年の新しい WSL2 のデフォルトカーネルは `6.6.y`（ブランチ例：`linux-msft-wsl-6.6.y`）以降へと進化しています。ビルド前にまず `uname -r` で現在の環境バージョンを確認し、[WSL2-Linux-Kernel](https://github.com/microsoft/WSL2-Linux-Kernel) から対応するブランチを選択することをおすすめします。

## 二、 Kernel Config 設定ファイルの準備

多くの解説記事では `WSL2-Linux-Kernel` リポジトリ内の `Microsoft/config-wsl` をそのままコピーして使う方法が紹介されていますが、**このやり方は強く非推奨**です。

**なぜ公式の `config-wsl` を使わないのか？** 公式の設定ファイルを見てみると、大量の項目が `M`（動的ロードモジュールとしてビルド）になっています。しかし WSL 環境では、モジュールパスや読み込み機構を別途きちんと設定しないと、カスタムカーネルに差し替えたあとで `M` に設定された機能（例：WireGuard など）が認識されず、そのまま動かなくなることがよくあります。

**ベストプラクティス：現在のシステムから設定ファイルをエクスポートする** — 今まさに安定稼働している WSL カーネルから Config を吸い出して使うのが最も確実です。エクスポートされた設定ファイルでは、有効な機能がデフォルトで `*`（Built-in、カーネル本体に直接組み込み）になっています。

以下のいずれかの方法で、設定ファイルを先ほど clone したソースコードのルートディレクトリに `.config` という名前でエクスポートします：

```bash
zcat /proc/config.gz > .config

# または
cat /proc/config.gz | gunzip > .config
```

## 三、 設定とビルド (Configuration and Compile)

### 1. Config の変更（TC/QoS サポートの追加）

先ほどと同じ理由で、`.config` テキストファイルを**直接手で編集してはいけません**。モジュール間には依存関係があるため、手動編集は非常にミスが起きやすいです。必ず `menuconfig` ツールを使って操作してください：

```bash
# ファイル名が .config でカレントディレクトリにある場合は、単に make menuconfig だけでも起動できます
make menuconfig KCONFIG_CONFIG=.config
```

**TC/QoS (Traffic Control / Quality of Service) 機能の追加：** 今回手動でカーネルをビルドした理由は、新しい QEMU パッケージが TC/QoS 機能を必要としたためです。TUI 画面が開いたら以下のパスへ移動し、中にある項目をすべて `Y` キーで `*`（Built-in）状態に変更します：`Networking support` -> `Network options` -> `QoS and/or fair queueing`

設定が終わったら `Save` を選んで保存し、終了します。

### 2. ビルド開始 (Compile)

設定を保存したらビルドを開始します。ターゲットに `bzImage` を明示的に指定するとより無駄なくビルドできます：

```bash
# システムの全 CPU コアを使ってビルド（最速）
make -j$(nproc) KCONFIG_CONFIG=.config bzImage

# もちろん、割り当てるコア数を指定したい場合（例：16 コア）は手動で指定可能：
make -j16 KCONFIG_CONFIG=.config bzImage
```

ビルドが完了すると、新しいカーネルファイルは次の場所に生成されます：`arch/x86/boot/bzImage`

## 四、 カスタム Kernel の差し替えと利用

ビルドした `bzImage` を Windows ホスト上の任意のフォルダ（例：`C:\WSL_Kernel\bzImage`）にコピーします。

### 方法 A：グローバル設定 `.wslconfig` を変更する（強く推奨 🌟）

これは Microsoft 公式でも最も推奨されており、安全な方法です。Windows 側で `C:\Users\<あなたのユーザー名>\.wslconfig` ファイルを編集します：

> **注意：** Windows パス内のバックスラッシュ `\` は `\\` とエスケープして記述しないと反映されません。

```ini
# Main WSL Setting Section
[wsl2]
# WSL 上での Hypervisor 機能を有効化（QEMU/KVM に必須）
nestedVirtualization=true

# カスタム Kernel ファイルの場所を指定
kernel=C:\\WSL_Kernel\\bzImage

# WSL の最大 RAM 使用量を制限（単位は GB/MB が利用可能）
memory=16GB
```

設定後、PowerShell で `wsl --shutdown` を実行して WSL を完全に終了し、再度起動すればカスタムカーネルが読み込まれます（`uname -r` でバージョンを確認できます）。

### 方法 B：Windows のデフォルト Kernel を直接上書きする（極めて非推奨 ❌）

Windows が標準で WSL カーネルを保存しているパスは以下の場所でした：`C:\Windows\system32\lxss\tools\kernel`

> [!info] Updated 2026-11-27
> `C:\Windows\system32\lxss\tools\kernel` は、初期の Windows OS に組み込まれていた旧世代の WSL にのみ該当します。現在 Microsoft Store 経由でインストール・更新されるモダンな WSL（Windows 10/11 の標準構成）では、カーネルファイルは保護された `WindowsApps` ディレクトリ内に配置されています。必ず方法 A の `.wslconfig` を使ってカスタムカーネルを読み込んでください。

ビルドした `bzImage` を `kernel` にリネームしてこのフォルダに放り込み、直接上書きすることも可能ではありました（管理者権限が必要で、事前に WSL を完全に shutdown する必要あり）。**メリット：** 何も設定しなくてもそのまま適用される。**致命的な欠点：** 万が一自分でビルドしたカーネルにバグがあって起動できなくなった場合、デフォルトの復旧環境すら失われて非常に厄介なことになるため、この方法は絶対におすすめしません。
