## 1. はじめに：モダンなパッケージ管理と Nala（推奨）

Debian 系ディストリビューションでは、低レイヤーのパッケージ管理ツールとして `dpkg` が動作しており、日常的にはより高機能な `apt` コマンド（従来の `apt-get` の後継）がよく使われます。

**おすすめツール：Nala**

Arch 系の `yay` のような見やすく直感的な UI に慣れているなら、Debian / Ubuntu に `nala` を導入することを強くおすすめします。`nala` は `apt` のフロントエンド代替ツールで、見やすい出力フォーマット、並列ダウンロードによる高速化、履歴からのロールバック機能を備えています。

```bash
# Nala をインストール
sudo apt update
sudo apt install nala
```

インストール後は、普段使っている `apt` コマンドをほぼそのまま `nala` に置き換えられます（例：`sudo nala update`）。以下の基本コマンドは標準の `apt` を基準に解説していますが、基本的な考え方はどちらも共通です。

## 2. 基本メンテナンス：インストールとシステム更新

**1. システム全体の更新**

Debian 系の更新は2ステップで行います。まずローカルのパッケージ一覧を更新し、その後に実際のアップグレードを実行します。

```bash
sudo apt update && sudo apt upgrade -y
```

> **発展知識：`apt upgrade` と `apt full-upgrade` の違い**
>
> - **`upgrade`（安全なアップグレード）：** 既存パッケージの更新のみを行います。あるパッケージの新バージョンをインストールするために他の古いパッケージの「削除」が必要な場合、`upgrade` はそのパッケージの更新を**スキップ**し、安定性を優先して現状を維持します。
> - **`full-upgrade`（完全なアップグレード）：** アップグレードの妨げとなる古い依存パッケージの**削除**を許可して更新を進めます。主にディストリビューションのメジャーアップグレード（例：Ubuntu 22.04 から 24.04 への更新）や、依存関係が競合して更新が進まない場合に使用します。
>   _(注：旧コマンドの `apt-get dist-upgrade` に相当します)_

**2. パッケージの検索とインストール**

```bash
# 特定のパッケージをインストール
sudo apt install <パッケージ名>

# パッケージを検索（正規表現に対応）
apt search <キーワード>
```

## 3. パッケージのアンインストールと「孤立パッケージ（Orphans）」の整理

Debian 系でアンインストールする際によくある失敗は、`remove` だけを実行して設定ファイルや不要な依存パッケージをシステムに残してしまうことです。

**1. 本体のクリーンな削除**

- **通常削除：** プログラム本体のみを削除し、`/etc` 配下で変更した設定ファイルは保持します。

  ```bash
  sudo apt remove <パッケージ名>
  ```

- **完全削除（Purge）：** グローバルな設定ファイルも含めてすべて削除します（ユーザーのホームディレクトリ `~/.config/` 内の設定は対象外です）。

  ```bash
  sudo apt purge <パッケージ名>
  ```

**2. 孤立パッケージ（Orphans）の削除**

あるソフトウェアをインストールする際に自動で入った依存パッケージは、本体を削除した後も残ります。Debian にはこれらを整理するコマンドが標準で用意されています。

```bash
# 不要になった孤立パッケージをすべて削除
sudo apt autoremove

# 発展：孤立パッケージの設定ファイルもあわせて完全に削除（推奨）
sudo apt --purge autoremove
```

## 4. ディスク容量の解放：キャッシュの削除（Cache）

`apt install` でダウンロードした `.deb` ファイルは、毎回 `/var/cache/apt/archives/` にキャッシュされます。長期間稼働している VM やディスク容量が限られた環境では、これがかなりの容量を圧迫します。

**1. キャッシュの手動削除**

```bash
# 安全な削除：「リポジトリからすでにダウンロードできなくなった」古いバージョンのキャッシュのみを削除
sudo apt autoclean

# 完全削除：キャッシュディレクトリ内のファイルをすべて削除（最大限の空き容量を確保）
sudo apt clean
```

> **自動化のヒント：** Debian / Ubuntu には標準で定期実行タスクが組み込まれています。`unattended-upgrades` をインストールしていれば、バックグラウンドで古いキャッシュを自動削除してくれるため、Arch のように手動で systemd Timer を書く必要はありません。

## 5. 緊急時の対処：ダウングレードとバージョン固定（Downgrade & Hold）

Debian 系は比較的安定していますが、サードパーティ製の PPA やリポジトリを追加している場合、更新後にソフトウェアが動かなくなることがあります。

**1. 過去のバージョンを確認する**

まず、リポジトリ上にダウングレード可能な旧バージョンが残っているかを確認します。

```bash
apt-cache madison <パッケージ名>
# または
apt list -a <パッケージ名>
```

これにより、利用可能なすべてのバージョン番号（例：`1.2.3-1ubuntu2`）が出力されます。

**2. ダウングレードの実行**

戻したいバージョン番号が見つかったら、`=` でバージョンを明示指定してインストールします（不具合のある新バージョンを強制的に上書きします）。

```bash
sudo apt install <パッケージ名>=<バージョン番号>
```

**3. ⚠️ 重要ステップ：バージョンを固定して再アップグレードを防ぐ（Hold）**

ダウングレード後、次にうっかり `apt upgrade` を実行して再び最新化されてしまうのを防ぐため、パッケージを「固定（hold）」しておく必要があります。

```bash
sudo apt-mark hold <パッケージ名>
```

hold されたパッケージは、新しいバージョンが公開されても `apt` によって自動的に更新対象から除外されます。

**4. バージョン固定を解除する（Unhold）**

公式から修正版がリリースされ、再びアップグレードしてよくなった場合は、固定を解除するだけです。

```bash
sudo apt-mark unhold <パッケージ名>
```

固定解除後は、次回の `apt upgrade` から通常どおりアップグレードされるようになります。

## 6. 発展：サードパーティ製リポジトリと GPG 鍵の正しい追加方法（apt-key からの移行）

以前は Docker、Node.js、Grafana などのサードパーティ製リポジトリを追加する際、`sudo apt-key add` で GPG 鍵を登録するのが一般的でした。しかし現在これを行うと、**apt-key is deprecated** という警告が表示されます。

**なぜ非推奨になったのか？** `apt-key` は鍵をシステム全体の「グローバル信頼ストア」（`/etc/apt/trusted.gpg`）に追加してしまいます。つまり、小さな外部ソフトの鍵を1つ追加しただけで、その鍵が理論上システムコアのパッケージさえも署名・偽造できてしまうという重大なセキュリティリスクがありました。

**現在の標準手順（Signed-by による紐付け方式）：** 現在の推奨方式では、鍵を専用ディレクトリに個別に保存し、設定ファイル内で「このリポジトリは特定の鍵でのみ検証する」と厳密に指定します。

以下は Ubuntu 22.04+ および Debian 12+ の規約に沿った標準的な手順です（架空の `example` リポジトリを追加する例）。

**1. 鍵を保管する専用ディレクトリを作成** 現在はサードパーティの鍵を `/etc/apt/keyrings/` にまとめるのが推奨されています（古い環境ではディレクトリが存在しない場合があるため事前に作成します）。

```bash
sudo mkdir -p /etc/apt/keyrings
```

**2. 鍵をダウンロードしてバイナリ形式へ変換（Dearmor）** 多くのサードパーティが配布している鍵は ASCII テキスト形式（`.asc` や `.pub`）ですが、現在の `apt` ではバイナリ形式の `.gpg` ファイルが推奨されています。`curl` でダウンロードし、`gpg --dearmor` で変換して先ほどのディレクトリに保存します。

```bash
curl -fsSL https://example.com/key.pub | sudo gpg --dearmor -o /etc/apt/keyrings/example.gpg
```

**3. リポジトリを追加し、鍵を紐付ける** `/etc/apt/sources.list.d/` にリストファイルを作成します。**最も重要なポイントは、`deb` の後ろに `[signed-by=...]` を記述することです。**

```bash
echo "deb [arch=amd64 signed-by=/etc/apt/keyrings/example.gpg] https://example.com/apt stable main" | sudo tee /etc/apt/sources.list.d/example.list
```

> **解説：** `signed-by=/etc/apt/keyrings/example.gpg` を指定することで、システムは `example.com` から取得するパッケージの検証にのみこの鍵を使用し、他のシステムパッケージの検証には一切関与しなくなります。

**4. パッケージ一覧を更新する** 最後にキャッシュを更新すれば、非推奨（deprecation）の警告は表示されなくなります。

```bash
sudo apt update
```

> [!info] Updated 2026-11-27
> 比較的新しい **Ubuntu 24.04+** および **Debian 12 / 13+** 環境では、以下のモダンな運用ポイントもあわせて推奨されます。
> 1. **ディレクトリと鍵のパーミッション**：ディレクトリ作成時は `sudo mkdir -p -m 0755 /etc/apt/keyrings` を指定し、変換後の `.gpg` ファイルも全ユーザーが読み取れる権限（`sudo chmod a+r /etc/apt/keyrings/example.gpg`）にしておくと、`apt update` を実行する低権限ユーザー `_apt` が鍵を読み込めないトラブルを防げます。
> 2. **アーキテクチャの動的取得**：ARM64（Raspberry Pi など）ホストで `arch=amd64` をハードコードするとパッケージを取得できなくなるため、`arch=$(dpkg --print-architecture)` のように動的に取得する記述が推奨されます。
> 3. **DEB822 `.sources` 形式**：新しいシステムでは従来の1行形式 `.list` から、構造化された `/etc/apt/sources.list.d/example.sources`（`Signed-By:` フィールドを使用）への移行が進んでいます。APT 3.0+（Debian 13 / Ubuntu 24.10+）では `sudo apt modernize-sources` を実行することで、既存の `.list` を `.sources` 形式へ自動変換することも可能です。
