## 1. 容量の特定：何がディスクを食い潰しているのか？

システムからアラートが出たりディスクが満杯になったりした際は、闇雲に削除せず、まず容量の内訳を特定します。

### 1.1 Docker ネイティブの容量分析

Docker 組み込みの分析ツールを使い、容量を占有しているのが Images、Containers、Local Volumes、Build Cache のどれかを素早く特定します。

```bash
# Docker 全体のリソース使用量サマリーを表示
docker system df

# 各項目の詳細内訳を表示（コンテナ ID、イメージサイズ、ボリューム共有情報を含む）
docker system df -v
```

### 1.2 Linux システムレベルでの調査（肥大化した隠しファイルを突き止める）

Docker のデフォルト保存パスは `/var/lib/docker` です（以下の操作には通常 `root` または `sudo` 権限が必要です）。`docker system df` に異常が出ているのに原因が掴めない場合、大抵は `/var/lib/docker/containers/` 配下に蓄積された標準出力ログ（`*-json.log`）が犯人です。

```bash
# /var/lib/docker 配下でサイズが大きい上位 20 件のファイル・ディレクトリを抽出（他ファイルシステムへの跨ぎ走査を防止）
sudo du -ahx /var/lib/docker | sort -rh | head -n 20

# すべてのコンテナの JSON Log サイズを調査し、容量の大きい順にソート
sudo find /var/lib/docker/containers/ -name "*-json.log" -exec du -h {} + | sort -rh | head -n 20
```

## 2. 緊急処置：Log ファイル肥大化の応急処置（オンライン空化）

特定のコンテナのログが数十 GB に達しているのを発見しても、**絶対に `rm -f <container_id>-json.log` で直接削除してはいけません**！

> **なぜ `rm` を使ってはいけないのか？** Linux カーネルでは、Docker デーモン（`dockerd`）がそのファイルのファイルディスクリプタ（FD）を開いたままにしている限り、ファイル参照が削除されても inode は `(deleted)` 状態のまま残り、Docker サービスを再起動するまで**ディスク容量は解放されません**。

### 正しい空化方法：`truncate`

`truncate` コマンドを使ってファイル長を 0 に切り詰めることで、ファイルディスクリプタを維持したまま即座にディスク容量を返還できます。

```bash
# 構文：
# sudo truncate -s 0 /var/lib/docker/containers/<CONTAINER_ID>/<CONTAINER_ID>-json.log

# 例：単一コンテナのログを空にする
sudo truncate -s 0 /var/lib/docker/containers/a1b2c3d4e5f6.../a1b2c3d4e5f6...-json.log

# 万能応急コマンド：ホスト上の 100M を超えるすべての Docker json-log を一括でゼロにする
sudo find /var/lib/docker/containers/ -name "*-json.log" -size +100M -exec truncate -s 0 {} \;
```

## 3. 根本対策：ログ上限の制限と自動ローテーション (Log Rotation)

空にするのはあくまで応急処置であり、Log Rotation を設定しなければログはいずれ再びディスクを埋め尽くします。制限方法には「グローバルデフォルト」と「個別プロジェクト／コンテナ指定」の 2 通りがあります。

### 方式 A：グローバル設定 (`/etc/docker/daemon.json`) —— 強く推奨

設定後、以降に新規作成されるすべてのコンテナがこの上限ルールを継承します。

1. `/etc/docker/daemon.json` を編集します：

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "50m",
    "max-file": "3"
  }
}
```

- `max-size`：単一ログファイルがこのサイズに達するとローテーションが発動します（`50m` や `100m` など）。
- `max-file`：保持するローテーションバックアップファイルの上限数。この数を超えると最も古いファイルが自動的に上書きされます。この例では最大 `50m * 3 = 150m` を占有します。

2. 設定を再読み込みし、Docker サービスを再起動します：

```bash
systemctl daemon-reload
systemctl restart docker
```

> [!info] Updated 2026-11-27
> 上記のリロードコマンドには 2 点の注意事項があります：
> 1. `systemctl daemon-reload` は systemd の `.service` ユニットファイルを再読み込みするためのものであり、`/etc/docker/daemon.json` を変更した際には実行**不要**です。
> 2. `systemctl restart docker` はホスト上で稼働中のすべてのコンテナを中断・再起動します（事前に `"live-restore": true` を有効にしている場合を除く）。ホットリロードに対応した `daemon.json` オプションのみを適用したい場合は `sudo systemctl reload docker` を先に実行できますが、`reload` と `restart` のいずれであっても、`log-driver` と `log-opts` が適用されるのはそれ以降に**新規作成**されたコンテナのみです。
> 3. 下の例では、すでに `docker compose down` を実行してコンテナとネットワークが削除されているため、続く `docker compose up -d` で再作成が行われ、`--force-recreate` を追加する必要はありません。ネットワークを削除せずにコンテナだけをその場で再作成したい場合は、`docker compose up -d --force-recreate` を直接実行してください。

> **重要な落とし穴の注意**：`daemon.json` の変更は**再起動後に「新規作成」されたコンテナにのみ有効**です。既存のコンテナに適用するには再作成が必要です：
>
> ```bash
> # 従来の docker run で起動したコンテナ：
> docker stop <name> && docker rm <name> && docker run ...
>
> # Docker Compose で管理しているコンテナ：
> docker compose down && docker compose up -d
> ```

### 方式 B：Compose プロジェクトでの個別設定 (`compose.yaml`)

高トラフィックの Nginx やデータベース同期サービスなど、特定のアプリケーションに個別のログクォータを指定したい場合は、サービスレベルで宣言できます。

```yaml
services:
  app-service:
    image: my-app:latest
    logging:
      driver: "json-file"
      options:
        max-size: "10m"
        max-file: "3"
```

変更を適用します：

```bash
docker compose up -d --force-recreate
```

## 4. 容量回収コマンド大全 (Prune シリーズ)

クリーンアップを行う前に、本番データの誤削除を防ぐため、各コマンドの影響範囲を必ず把握しておいてください。

### 4.1 コンテナとイメージの安全なクリーンアップ

```bash
# 1. 安全なクリーンアップ（日常運用向け）
# 削除対象：停止中の全コンテナ、未使用ネットワーク、ダングリングイメージ（dangling：タグのない <none> イメージ）
docker system prune -f

# 2. ディープクリーンアップ（大量の空き容量を確保）
# 削除対象：停止中の全コンテナ、未使用ネットワーク、および「どのコンテナからも参照されていないすべてのイメージ」
# 注意：アプリを再起動する際にイメージの再 pull が必要になります
docker system prune -a -f

# 3. ビルドキャッシュの削除（Build Cache）
# Dockerfile のビルド過程で残ったキャッシュ。長年の蓄積で数十 GB を占有することがよくあります
docker builder prune -a -f
```

### 4.2 ボリュームのクリーンアップ（最も危険、極めて慎重に扱うこと）

デフォルトでは、`docker system prune` は Volume を**自動削除しません**。Volume には通常、データベースや永続データが保存されているためです。

```bash
# 孤立した Volume を一覧表示（どのコンテナにもマウントされていない volume）
docker volume ls -f dangling=true

# すべての孤立 Volume を削除（警告：停止メンテナンス中で将来また使う予定の DB コンテナがある場合、データが永久に失われます！）
docker volume prune -f

# 最終クリーンアップ（未マウントの Volume も含めて一掃。環境初期化時以外は安易に使用しないこと）
docker system prune -a --volumes -f
```

## 5. 自動パンク防止機構：Linux Logrotate によるシステムバックアップ

環境内に設定変更が難しく `max-size` を適用できないレガシーコンテナがある場合は、ホスト OS の `logrotate` を用いて定期バックアップ処理を構築できます。

`/etc/logrotate.d/docker-containers` を作成します（`*-json.log` に正確に一致させることを推奨）：

```bash
/var/lib/docker/containers/*/*-json.log {
    rotate 3
    daily
    copytruncate
    compress
    missingok
    notifempty
    maxsize 100M
}
```

- **`copytruncate`**：非常に重要です。ログファイルを先に複製してから元ファイルをゼロ長に切り詰めるため、Docker のファイルディスクリプタを途切れさせず、`truncate` の自動実行と同等の効果を発揮します。

設定が正しいかテストします（実際の変更は行われません、`sudo` 権限が必要です）：

```bash
sudo logrotate -d /etc/logrotate.d/docker-containers
```

## 6. メンテナンス用フローチャート早見表

```bash
ディスク容量アラート (100% Full)
  │
  ├─ 1. docker system df (Images/Build Cache か Container Log かを確認)
  │     └─ Build Cache の場合 ──> docker builder prune -f
  │     └─ Dangling Images の場合 ──> docker image prune -f
  │
  ├─ 2. Logs 肥大化の場合 (du -ahx /var/lib/docker | grep -i json.log)
  │     └─ 即時応急処置 ──> truncate -s 0 <path_to_log>
  │     └─ 恒久対策 ──> /etc/docker/daemon.json を設定 (max-size/max-file)
  │                     └─ コンテナ再作成で反映 (docker compose down && up -d)
  │
  └─ 3. 定期メンテナンス ──> cron ジョブを設定して docker system prune -f を実行
```

> [!info] Updated 2026-11-27
> フローチャート 2 番目の最終行 `(docker compose down && up -d)` でコマンドプレフィックスが抜けており、正しくは `docker compose down && docker compose up -d`（または `docker compose up -d --force-recreate`）です。また、`grep -i json.log` の `.` は正規表現で任意の 1 文字を表すため、正確に一致させるには `grep -i 'json\.log'` と記述することを推奨します。
