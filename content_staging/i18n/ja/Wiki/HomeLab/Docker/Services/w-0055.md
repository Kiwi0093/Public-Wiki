## 1. コアメカニズムとネットワーク構成

WireGuard は **ピアツーピア（Peer-to-Peer, P2P）** の概念を採用しており、構成内のすべてのマシンは本質的に「Peer」です。通常、固定のグローバル IP を持つホストを「Server / Relay Node」として扱います。

```
[クライアント (Phone / Laptop)] (WireGuard IP: 10.13.13.2)
        │
        │ UDP (暗号化パケット、デフォルトポート 51820)
        ▼
[WireGuard Server コンテナ] (WireGuard IP: 10.13.13.1 / ホスト Public IP:Port)
        │
        ├─► [LAN 内デバイス (LAN アクセス)] (192.168.1.0/24)
        └─► [インターネット (フル・トンネル転送)] (0.0.0.0/0)
```

- **UDP プロトコル**：WireGuard は完全に UDP 上で動作し、データ通信がない間はプローブパケットを一切送信しません。ポートスキャンに対して「無応答（サイレント）」として振る舞うため、非常に高い耐スキャン性能を持ちます。
    
- **Cryptokey Routing（暗号鍵ルーティング）**：サーバーは各 Client の **Public Key** と割り当てられた内部 IP を強固に紐付けます。署名が正しく、かつ送信元 IP が宣言と一致するパケットのみが受理されます。
    

## 2. Docker Compose によるサーバーデプロイ (LinuxServer.io)

LinuxServer.io イメージの最大の特徴は、起動時に環境変数 `PEERS` で宣言した名称に基づき、**対応するクライアント設定ファイル（`peer_*.conf`）とターミナル用の QR コードを自動生成**してくれる点にあり、手動での鍵生成やルーティング設定の手間を省けます。

### ステップ 1：専用ディレクトリの作成

```bash
sudo mkdir -p /opt/wireguard/config
```

### ステップ 2：`docker-compose.yml` 完全設定

`/opt/wireguard/docker-compose.yml` に以下を定義します。

```yaml
services:
  wireguard:
    image: ghcr.io/linuxserver/wireguard:latest
    container_name: wireguard
    restart: unless-stopped
    cap_add:
      - NET_ADMIN
      - SYS_MODULE
    environment:
      - PUID=1000
      - PGID=1000
      - TZ=Asia/Taipei
      # 1. 外部アクセスアドレス（固定グローバル IP または DDNS ドメイン名）
      - SERVERURL=vpn.example.com
      # 2. 外部リッスン UDP ポート
      - SERVERPORT=51820
      # 3. クライアント名リスト（カンマ区切り、対応する設定ファイルが自動生成されます）
      - PEERS=phone,laptop,ipad
      # 4. Client に割り当てる DNS サーバー（1.1.1.1、8.8.8.8、または LAN 内 AdGuard Home IP など）
      - PEERDNS=1.1.1.1
      # 5. WireGuard 内部仮想サブネット（Server は自動的にこのサブネットの .1 を取得）
      - INTERNAL_SUBNET=10.13.13.0/24
      # 6. クライアントへ配布するデフォルトの AllowedIPs 範囲（0.0.0.0/0 は全トラフィック転送）
      - ALLOWEDIPS=0.0.0.0/0
    volumes:
      - /opt/wireguard/config:/config
      - /lib/modules:/lib/modules:ro
    ports:
      - "51820:51820/udp"
    sysctls:
      - net.ipv4.conf.all.src_valid_mark=1
```

> **主要パラメータと権限のポイント**：
> 
> - `cap_add: [NET_ADMIN, SYS_MODULE]`：コンテナがホストの仮想ネットワークインターフェース（TUN）を操作し、WireGuard カーネルモジュールをロードするために必要です。
>     
> - `/lib/modules:/lib/modules:ro`：コンテナ内部からホストの WireGuard カーネルドライバをロードし、最大限のパフォーマンスを引き出すためにマウントします（Linux 5.6+ カーネルには標準内蔵されています）。
>     
> - `net.ipv4.conf.all.src_valid_mark=1`：マルチルーティングテーブル環境でパケットが rp_filter によって破棄されるのを防ぎます。
>     

サービスを起動します。

```bash
docker compose up -d
```

## 3. クライアント設定の取得と接続方法

### 3.1 モバイル端末 (Android / iOS)

1. Google Play または App Store から公式 **WireGuard** アプリをインストールします。
    
2. コンテナが生成した QR コードを確認します。
    
    
   ```bash
    # 特定 Peer の QR コードを表示
    docker compose logs -f wireguard
    # またはコンテナ内ツールで特定の peer（例：phone）を指定して表示
    docker compose exec wireguard /app/show-peer phone
   ```
    
3. スマホの WireGuard アプリを開き、`+` ボタン -> 「QR コードをスキャン (Scan from QR code)」を選択すれば一瞬でインポートして有効化できます。
    

### 3.2 デスクトップ版・Linux クライアント向け設定ファイルの取得

生成されたすべての設定ファイルは、ホスト側のマウントディレクトリに保存されています。

```bash
# 生成された設定ファイルを確認
ls -l /opt/wireguard/config/peer_laptop/
# 内容：
# - peer_laptop.conf (標準設定ファイル)
# - peer_laptop.png  (QR コード画像ファイル)
# - privatekey-peer_laptop / publickey-peer_laptop
```

## 4. Linux クライアント設定の実践（Arch / Manjaro / Debian / Ubuntu 例）

Linux デスクトップまたはサーバーでは、主に従来の `wg-quick` CLI ツールを使う方法と、デスクトップのネットワーク管理と統合された `NetworkManager` を使う方法の 2 通りがあります。

### 方法 A：`wg-quick` CLI を使用（サーバーや軽量環境向け）

1. ツールパッケージをインストールします。
    
    
   ```bash
    # Arch / Manjaro
    sudo pacman -S wireguard-tools
    
    # Ubuntu / Debian
    sudo apt-get install -y wireguard-tools
   ```
    
2. 設定ファイルを配置します。
    
    サーバー側で生成された `peer_laptop.conf` をクライアントの `/etc/wireguard/` にコピーし、好みのインターフェース名（例：`wg0.conf`）に変更します。
    
    
   ```bash
    sudo mkdir -p /etc/wireguard
    sudo cp peer_laptop.conf /etc/wireguard/wg0.conf
    # 鍵ファイルの権限を厳格に制限（設定しないと wg-quick が警告を出します）
    sudo chmod 600 /etc/wireguard/wg0.conf
   ```
    
3. 接続の開始と停止：
    
    
   ```bash
    # 接続開始（インターフェース名はファイル名の wg0 になる）
    sudo wg-quick up wg0
    
    # 接続状態と通信量 (Transfer RX/TX) を確認
    sudo wg show
    
    # 接続切断
    sudo wg-quick down wg0
   ```
    
4. （任意）OS 起動時の自動接続を設定：
    
    
   ```bash
    sudo systemctl enable wg-quick@wg0
   ```
    

### 方法 B：NetworkManager / GUI へのインポート（デスクトップ環境向け）

GNOME や KDE などのデスクトップ環境を使用している場合、`nmcli` で一括インポートすれば、システム右上のネットワークアイコンからオン／オフを切り替えられます。

```bash
# 設定ファイルをインポートして接続プロファイルを作成
sudo nmcli connection import type wireguard file /etc/wireguard/wg0.conf

# 接続を有効化
nmcli connection up wg0

# 接続を切断
nmcli connection down wg0
```

_（インポート後は、システムの「ネットワーク設定 (Network Settings)」GUI 画面からも自由に切り替えや編集が可能です）_。

## 5. ハマりやすいポイント：`AllowedIPs` ルーティング設計（フル・トンネル vs. スプリット・トンネル）

クライアント設定ファイル内の `AllowedIPs` は、「VPN をオンにした途端に元のネットが切れる」「サーバー上の他のサービスに繋がらない」といったトラブルの最大の原因になります。これには**二重の役割**があります。

1. **ローカルルーティングの注入**：ローカル端末のどの宛先 IP トラフィックを WireGuard トンネルに流すかを決定します。
    
2. **受信パケットのフィルタリング**：WireGuard インターフェースがどの送信元 IP からのパケットのみを受け入れるかを決定します。
    

### シナリオ 1：フル・トンネル (Full Tunnel / 全トラフィック転送)

外出先で公衆 Wi-Fi に接続する際、**すべての通信トラフィック**を自宅や VPS の WireGuard サーバー経由で外に出したい場合：

```ini
[Peer]
# すべての IPv4 および IPv6 サブネットを含む
AllowedIPs = 0.0.0.0/0, ::/0
```

> **注意**：
> 
> `0.0.0.0/0` を設定すると、WireGuard がデフォルトゲートウェイ（Default Gateway）を掌握します。クライアント側が属する LAN 内に別のサービスやローカルサーバーがある場合は、ローカル LAN のルーティングが除外されるよう確認が必要な場合があります。

### シナリオ 2：スプリット・トンネル (Split Tunnel / LAN 内デバイスへのアクセスのみ)

自宅やサーバルームの内部デバイス（NAS、HomeLab、内部 Web UI など）へ安全にアクセスすることだけを目的とし、YouTube や Google などの通常通信はこれまで通りローカル回線を使いたい場合：

```ini
[Peer]
# リモートの LAN サブネット (例: 192.168.1.0/24) と WireGuard 自体のサブネット (10.13.13.0/24) のみを VPN 経由にする
AllowedIPs = 10.13.13.0/24, 192.168.1.0/24
```

## 6. NAT 越え・キープアライブ：`PersistentKeepalive`

WireGuard はデフォルトでステートレスです。Client が NAT（家庭用ルーター、モバイル回線 4G/5G など）配下にある場合、ルーターの NAT 変換テーブルは数十秒〜数分でタイムアウトした UDP セッション状態を破棄してしまいます。その結果、「**Client から Server へはリクエストを送れるのに、Server から能動的にデータを送信しても Client に届かない**」（たとえば Client 側でのプッシュ通知の遅延など）という現象が起きます。

### 解決策：

クライアント設定ファイルの `[Peer]` セクションに以下を追記します。

```ini
[Peer]
# 25 秒ごとにサーバーへ軽量な Keepalive パケットを送信し、NAT 穴あけ状態を維持
PersistentKeepalive = 25
```

_（LinuxServer.io がデフォルトで生成する peer.conf には通常この行がすでに含まれています）_。

## 7. サーバー側のカーネル転送とよくあるトラブルシューティング (Troubleshooting)

| **異常現象** | **根本原因** | **対処手順** |
| :--- | :--- | :--- |
| **接続後、Client 側でインターネットに一切繋がらない** | ホスト側 Linux カーネルで IPv4 Forwarding が有効化されていない | **ホスト機**で以下を実行：<br />`echo "net.ipv4.ip_forward = 1" \| sudo tee /etc/sysctl.d/99-wireguard.conf`<br />`sudo sysctl -p /etc/sysctl.d/99-wireguard.conf` |
| **接続はできるが通信量が TX のみ増え、RX が 0 のまま** | 1. 外部ファイアウォールで UDP 51820 が許可されていない。<br />2. `SERVERURL` または `SERVERPORT` の記述ミス。<br />3. クラウド環境（OCI、AWS、GCP など）のセキュリティグループで UDP の開放漏れ。 | 1. クラウド管理画面で **`0.0.0.0/0 -> UDP 51820`** が許可されているか確認。<br />2. ホスト機でリッスン状態を確認：`sudo ss -ulpn \| grep 51820`。 |
| **スマホ Client の接続は正常だが、IP 切り替え後に時々固まる** | MTU 値が大きすぎてパケット分割が起き、キャリア側に破棄されている | スマホ側では通常デフォルトの 1420 で問題ありませんが、モバイル回線で不安定な場合は、クライアントの `[Interface]` に `MTU = 1280` を手動で設定してみてください。 |
| **動的に新しい Peer を追加したい** | Compose ファイルの環境変数を変更して反映する | 1. `docker-compose.yml` を編集し、`PEERS=` の末尾に新しい名前を追加（例：`PEERS=phone,laptop,ipad,newpc`）。<br />2. `docker compose up -d` を実行すると、コンテナが既存の Peer に影響を与えずに新しい Peer の設定ファイルを自動追加生成します。 |
