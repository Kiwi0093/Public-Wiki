## 1. アーキテクチャ設計とマルチホストのセキュリティトポロジ

単一ホスト上であれば `/var/run/docker.sock` を直接マウントできますが、コンテナが複数の物理マシンや VPS に分散している場合、暗号化されていない Docker Socket をそのまま外部ネットワークに公開するのは root 権限昇格を許すのと同義です。

そのため、マルチホスト監視構成における標準的なセキュリティ対策は **`docker-socket-proxy`** を導入することです。

```
[Uptime Kuma セントラルサーバー]
       │
       ├─► ローカルコンテナ監視: ローカルの /var/run/docker.sock:ro をマウント
       │
       ├─► リモートホスト A 監視: TCP 2375 経由でクエリ (docker-socket-proxy による読み取り専用保護)
       │         ▲
       │         └─ [リモートノード A] ── docker-socket-proxy ── /var/run/docker.sock
       │
       ├─► 異常検知時 ───► Telegram Bot API ───► スマホ / グループへ即時プッシュ通知
       │
       └─► 外部ビジター ───► 専用ステータスページ (Status Page) ───► グラスモーフィズムダークテーマ表示
```

- **`docker-socket-proxy` の防御メカニズム**：内部の HAProxy によって Docker API リクエストをインターセプトします。`POST=0` を設定してすべての書き込み・作成・削除権限を無効化し、`CONTAINERS=1` などの読み取り専用エンドポイントのみを開放することで、公開された Docker ポートを悪用してホスト OS の権限を奪取する攻撃を防ぎます。

## 2. Docker Compose デプロイ構成

### 2.1 リモート被監視ノード：`docker-socket-proxy` のデプロイ（マルチホスト向け）

リモートの VPS または被監視ノード上に `/opt/dockerproxy/docker-compose.yml` を作成します：

```yaml
services:
  dockerproxy:
    image: ghcr.io/tecnativa/docker-socket-proxy:latest
    container_name: dockerproxy
    restart: unless-stopped
    environment:
      # 監視に必要な読み取り専用権限のみを開放
      - CONTAINERS=1
      - SERVICES=1
      - TASKS=1
      - POST=0
      - BUILD=0
      - COMMIT=0
      - CONFIGS=0
      - DISTRIBUTION=0
      - EXEC=0
      - IMAGES=0
      - INFO=0
      - NETWORKS=0
      - NODES=0
      - PLUGINS=0
      - SECRETS=0
      - SESSION=0
      - SWARM=0
      - SYSTEM=0
      - VOLUMES=0
    ports:
      # 内部ネットワークまたは WireGuard VPN セグメントのみでの開放を推奨。パブリックネットワーク経由の場合は必ずファイアウォールで送信元 IP を制限すること
      - "2375:2375"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
```

### 2.2 セントラルサーバー：Uptime Kuma 本体のデプロイ

`/opt/uptime-kuma/docker-compose.yml` を作成します：

```yaml
services:
  uptime-kuma:
    image: louislam/uptime-kuma:1
    container_name: uptime-kuma
    restart: unless-stopped
    ports:
      # デフォルトポートに直接バインド。前段に NPM / Traefik がある場合は外部ポートマッピングを外してよい
      - "3001:3001"
    volumes:
      - /opt/uptime-kuma/data:/app/data
      # ローカルコンテナ監視用にホストの socket をマウント
      - /var/run/docker.sock:/var/run/docker.sock:ro
    networks:
      - monitor-net
      # リバースプロキシ経由にする場合は proxy ネットワークに参加
      - proxy-network

networks:
  monitor-net:
    driver: bridge
  proxy-network:
    external: true
```

サービスを起動します：

```bash
docker compose up -d
```

> [!info] Updated 2026-11-27
> 元の設定にある `louislam/uptime-kuma:1` は旧 v1 ブランチです。新規デプロイでは安定版の `louislam/uptime-kuma:2` の使用を推奨します（v1 からアップグレードする場合は、事前にデータをバックアップし、公式のバージョン移行ガイドを確認してください）。

## 3. Telegram アラート Bot の連携手順

### ステップ A：BotFather から Bot Token を取得する

1. Telegram で公式 Bot `@BotFather` を検索します。

2. コマンド `/newbot` を送信します。

3. 指示に従い、Bot の表示名（Name）とユーザー名（Username、末尾は必ず `bot` にすること。例：`HomeLab_alert_bot`）を入力します。

4. 返却された **HTTP API Token**（形式例：`123456789:ABCdefGhIJKlmNoPQRsTUVwxyZ`）を保存します。

### ステップ B：個人またはグループの `chat_id` を取得する

1. Telegram で先ほど作成した Bot を検索し、**Start** をクリックするか任意のメッセージを送信します。

2. Chat ID を取得します：

    - **方法 1**：ブラウザで `https://api.telegram.org/bot<YOUR_BOT_TOKEN>/getUpdates` にアクセスし、返却された JSON 内にある `"chat":{"id": 123456789, ...}` を確認します。

    - **方法 2**：Telegram で `@userinfobot` を検索して Start をクリックすると、自分の数値 `Id` が直接返ってきます。

### ステップ C：Uptime Kuma に通知チャネルを紐付ける

1. Uptime Kuma 管理画面 (`http://<IP>:3001`) を開く -> 右上のアイコンをクリック -> **設定 (Settings)** -> **通知 (Notification)** -> **通知を設定 (Setup Notification)**。

2. タイプで **Telegram** を選択します：

    - **Bot Token**：先ほど取得した API Token を貼り付けます。

    - **Chat ID**：数値の ID を入力します。

3. **テスト (Test)** をクリックし、Telegram にテストメッセージが届くことを確認してから保存します。

## 4. 監視項目の作成 (Docker コンテナ監視)

左上の「**新しい監視項目を追加**」をクリックします：

- **ローカルコンテナの監視**：

    - **監視タイプ**：`Docker コンテナ (Docker Container)` を選択します。

    - **Docker ホスト (Docker Host)**：デフォルトの `/var/run/docker.sock` を選択します。

    - **コンテナ名/ID**：対象のコンテナ名（例：`nextcloud`、`gitea`）を入力します。

- **リモートノードコンテナの監視 (Socket Proxy 経由)**：

    1. **設定** -> **Docker ホスト** -> **Docker ホストを追加** へ進みます。

    2. 接続方式で `TCP Socket` を選択し、アドレスに `tcp://<REMOTE_VPS_IP>:2375` を入力します。

    3. 監視項目を追加する際、ドロップダウンメニューからそのリモートホストに切り替えれば、そのホスト上のコンテナ名を入力してクロスホスト監視ができます。

## 5. 高度な運用テクニック

### 5.1 「デッドマンズスイッチ (Dead Man's Switch)」：Push パッシブハートビート監視

通常の監視は対象へ能動的に Ping を行いますが、**バックアップスクリプトや NAS タスク、Cron Job が時間通りに完了したか**を確認したい場合は **Push モード** を使います：

1. 監視タイプで **「Push」** を選択し、ハートビート間隔（例：86400 秒 = 1 日）を設定します。

2. Kuma が専用の Webhook URL を生成します：`https://kuma.example.com/api/push/keyXYZ?status=up&msg=OK&ping=`

3. バックアップスクリプトの末尾に通知コマンドを追加します：

    ```bash
    curl -fsS -m 10 --retry 3 "https://kuma.example.com/api/push/keyXYZ?status=up&msg=BackupSuccess"
    ```

- スクリプトが異常終了したりハングしたりした場合、時間内に報告が届かないため Kuma が即座にアラートを発報します。

### 5.2 Webhook と連携した「サービス障害時の自動再起動 (Self-Healing)」

コンテナが異常停止した際、メッセージを通知するだけでなく、外部サービスを駆動して自動復旧させることができます：

1. 通知設定で **Webhook** を追加します。

2. Node-RED や軽量な Webhook サーバー（`adnanh/webhook` など）と連携させます。

3. `DOWN` イベントを受信した際、バックグラウンドサービスが自動的に `docker restart <container_name>` を実行することで障害の自己修復（Self-Healing）を実現します。

### 5.3 組み込みの SSL 証明書期限切れ間近アラート

監視タイプで **HTTP(s)** を選択してドメイン名を入力すると、Kuma が TLS 証明書チェーンを自動取得し、デフォルトで証明書の有効期限が切れる **21 日前・14 日前・7 日前** に自動で通知を送信します。これにより Let's Encrypt の自動更新失敗によるサービス停止を防げます。

## 6. 公開ステータスページ (Status Page) と Custom CSS グラスモーフィズム装飾

## 7. バックアップとリストア

Uptime Kuma のすべての監視項目、カスタムアラートルール、および履歴統計データは `/app/data/kuma.db`（SQLite）に保存されています：

```bash
# 1. データディレクトリのバックアップ
sudo tar -czvf /opt/backups/uptime-kuma-$(date +%F).tar.gz -C /opt/uptime-kuma data

# 2. 新しい環境へのバックアップ復元
sudo tar -xzvf /opt/backups/uptime-kuma-*.tar.gz -C /opt/uptime-kuma/
docker compose restart uptime-kuma
```

> [!info] Updated 2026-11-27
> 1. `/opt/uptime-kuma/data` のバックアップまたはリストアを行う前に、稼働中の SQLite（`kuma.db` WAL モード）でデータの不整合が起きないよう `docker compose stop uptime-kuma` を実行することを推奨します。
> 2. `/opt/backups/` ディレクトリ内に複数のバックアップファイルが存在する場合、リストアコマンドのワイルドカード `uptime-kuma-*.tar.gz` では `tar` がエラーになるため、具体的なバックアップファイル名を指定してください。
