## 1. Core Mechanisms and Version Limitations

- **KMS Activation Essence**: The KMS license period is **180 days**. Clients automatically send renewal requests to the KMS server every 7 days; if the server is online, it resets to 180 days after each renewal.
- **Supported Version Limitations**:
  - **Windows**: **Only supports Volume License editions, Pro, Enterprise, Education, and Windows Server**. Home Edition lacks KMS client components and cannot be activated directly (must be upgraded to Pro first).
  - **Office**: **Only supports Volume License editions (Office LTSC / Volume License)**. General retail editions (Retail / Click-to-Run Home editions) or Microsoft 365 subscription editions cannot be activated directly via KMS and require installing volume license editions through the Office Deployment Tool (ODT).
- **GVLK (Generic Volume License Key)**: Generic volume license keys publicly provided by Microsoft. Their sole purpose is to guide the system to "seek authentication from the KMS server within the local network," and they are not pirated serial numbers.

## 2. Docker Compose Server Deployment

`vlmcsd` resource consumption is extremely low (memory is typically less than 5MB), and it only needs to listen on the standard KMS protocol port **TCP 1688**.

### Step 1: Create Dedicated Directory

```bash
mkdir -p /opt/vlmcsd
cd /opt/vlmcsd
```

### Step 2: `docker-compose.yml` Configuration

```yaml
services:
  vlmcsd:
    image: mikolatero/vlmcsd:latest
    container_name: vlmcsd
    restart: unless-stopped
    ports:
      - "1688:1688"
```

Start the service and check logs:

```bash
docker compose up -d
docker compose logs -f
```

## 3. Windows Client Activation Steps

Open Command Prompt (CMD) as **Administrator** <span style="color:#e06c75"><del>or PowerShell</del></span> *(Updated 2026-11-27: The following example uses CMD's dedicated `::` comment syntax; please run it in CMD. If using PowerShell, replace `::` with `#`)*:

```bat
:: 1. (Optional) Clear previously bound product key
slmgr.vbs /upk

:: 2. Install the official Microsoft GVLK key for your corresponding version
slmgr.vbs /ipk <GVLK-KEY>

:: 3. Point to your vlmcsd server IP or internal network hostname
slmgr.vbs /skms <DOCKER_HOST_IP>:1688

:: 4. Trigger connection activation
slmgr.vbs /ato

:: 5. View detailed authorization status and expiration countdown
slmgr.vbs /dlv
```

## 4. Office Volume License Edition (LTSC) Deployment and Activation

Retail Office editions cannot authenticate directly with KMS; volume license editions must be installed.

### Step A: Acquire and Configure Office Deployment Tool (ODT)

1. Go to the official Microsoft website to download the **Office Deployment Tool (ODT)**.
2. Open the **[Office Customization Tool](https://config.office.com/deploymentsettings)** online configuration page:
   - Architecture: `64-bit`.
   - Products: **Office LTSC Professional Plus (Volume License)** (e.g., Office LTSC 2021 or 2024).
   - Licensing and activation: Select **KMS**.
   - Language: `Traditional Chinese (Taiwan)`.
   3. Export the configuration file, name it `configuration.xml`, and place it in the same directory where ODT (`setup.exe`) is extracted.

### Step B: Download and Install

Run CMD as Administrator in that directory:

```bat
:: 1. Pre-download installation files
setup.exe /download configuration.xml

:: 2. Execute local silent installation
setup.exe /configure configuration.xml
```

### Step C: Activate via OSPP.VBS

Navigate to the Office installation path (choose according to installation bitness):

```bat
:: 64-bit Office:
cd "C:\Program Files\Microsoft Office\Office16"

:: 32-bit Office (if installed on 64-bit Windows):
cd "C:\Program Files (x86)\Microsoft Office\Office16"
```

Execute the following commands in order:

```bat
:: 1. Set KMS server address
cscript ospp.vbs /sethst:<DOCKER_HOST_IP>

:: 2. (If key was not brought in) Manually specify the product GVLK
cscript ospp.vbs /inpkey:<OFFICE-GVLK-KEY>

:: 3. Trigger connection activation immediately
cscript ospp.vbs /act

:: 4. View authorization status and remaining days
cscript ospp.vbs /dstatus
```

## 5. Common Error Codes and Troubleshooting

| **Error Code** | **Description** | **Resolution** |
| :--- | :--- | |
| `0xC004F074` | Cannot connect to KMS server | Check Docker container operating status and ensure port 1688 is not blocked by host firewall. |
| `0xC004F038` | KMS count not sufficient | Microsoft standard requires 25 for Windows and 5 for Server. `vlmcsd` already simulates full count; if this error occurs, it means the image is too old or the counter is corrupted, please update the image. |
| `0xC004F015` | Key is invalid or version not supported | Current installation is Retail or Home edition, not Volume License. Need to replace GVLK or reinstall volume license edition. |

## 6. Microsoft Official Development Trends vs. The Future of Local KMS (vlmcsd)

As enterprise architectures comprehensively move toward remote work and cloud-native practices, Microsoft has made deep strategic adjustments to traditional licensing frameworks in recent years, directly impacting the practical use cases of local KMS tools:

### 6.1 Microsoft's De-KMS Trend

1. **Comprehensive Shift to Identity-Based Subscription Activation**:
   - On the enterprise side, Microsoft heavily promotes **Microsoft Entra ID (formerly Azure AD)** and **Microsoft Intune**.
   - Modern Windows 11/10 devices simply log in with a user account assigned to M365 (E3/E5 or A3/A5), and the OS seamlessly upgrades in-place from Pro to Enterprise without deploying a KMS server or entering a GVLK.
2. **Hybrid Work Makes Internal KMS Difficult**:
   - Traditional KMS requires communication with the internal KMS Host every 180 days (otherwise entering the grace period and reverting to unactivated). In Work from Anywhere environments, relying on VPN connections back to the office for KMS creates a heavy IT burden, and Microsoft is accelerating guiding enterprises to phase out on-premises KMS in favor of cloud activation.
3. **Office Fully Moving to SaaS (Microsoft 365 Apps)**:
   - Microsoft keeps compressing the status and support lifecycle of LTSC (Long-Term Servicing Channel) perpetual editions (e.g., reducing support duration from 10 years to 5 years in the past) and restricting new cloud collaboration features exclusively to M365 subscribers. This gradually marginalizes Office volume license editions that rely on KMS.

### 6.2 Future and Limitations of Tools Like vlmcsd

| **Evaluation Dimension** | **Current Status and Future Outlook** |
| :--- | :--- |
| **Short-term Outlook (Still Viable)** | In **air-gapped networks, industrial control networks, internal test HomeLabs, virtualization clusters (Proxmox / ESXi), and local Windows Server environments**, vlmcsd retains high convenience and irreplaceability, allowing offline VMs to activate and maintain testing functionality properly. |
| **Functional Limitations (Feature Gap)** | Office activated via vlmcsd only unlocks traditional offline features and **cannot use advanced cloud features supported by Microsoft's servers** (such as Copilot AI integration, Excel cloud data types, real-time multi-user collaboration, etc.), as these features require cloud account verification. |
| **Protocol Maintenance & Upgrade Risks** | When releasing new versions of Windows / Windows Server, Microsoft may adjust the KMS protocol version or RPC authentication mechanism. If the open-source community stops maintaining `vlmcsd` or fails to adapt to new signatures in time, next-generation systems (such as Windows 12) may experience incompatibility and failure with `vlmcsd`. |
| **Competition from Digital License (HWID) Tools** | In the personal user sector, the community has largely turned in recent years toward leveraging Microsoft's official accessibility upgrade channels or digital entitlement migration vulnerabilities (such as HWID / MAS writing motherboard hardware hashes directly to Microsoft's cloud servers to obtain permanent digital licenses), causing KMS tools that require periodic 180-day renewals to be heavily replaced on standard desktops. |
