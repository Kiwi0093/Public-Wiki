# Uptime Kuma Service Monitoring, Cross-Node Guarding, Real-Time Alerts, and Status Page Styling

> <img src='https://img.shields.io/badge/Status-Active-A8FF24?style=for-the-badge&labelWidth=100' height='38' />

![Docker](https://img.shields.io/badge/Docker-Supported-green?style=plastic&logo=docker)

## 1. Architecture Design and Multi-Host Security Topology

On a single host, you can mount `/var/run/docker.sock` directly; however, when containers are spread across multiple physical machines or VPSs, exposing an unencrypted Docker socket to the public internet is equivalent to granting root privilege escalation.

Therefore, the standard secure solution for multi-host monitoring is introducing **`docker-socket-proxy`**:

```
[Uptime Kuma Central Server]
       │
       ├─► Monitor local containers: mounts local /var/run/docker.sock:ro
       │
       ├─► Monitor remote Host A: queries via TCP 2375 (read-only protected by docker-socket-proxy)
       │         ▲
       │         └─ [Remote Node A] ── docker-socket-proxy ── /var/run/docker.sock
       │
       ├─► On anomaly trigger ───► Telegram Bot API ───► Real-time push to phone / group
       │
       └─► External visitors ───► Dedicated Status Page ───► Glassmorphism dark theme display
```

- **How `docker-socket-proxy` protects the host**: Under the hood, it intercepts Docker API requests via HAProxy. Setting `POST=0` disables all write, create, and delete permissions, exposing only read-only endpoints such as `CONTAINERS=1` to prevent attackers from escalating privileges and taking over the host via an exposed Docker port.

## 2. Docker Compose Deployment Configuration

### 2.1 Remote Managed Node: Deploy `docker-socket-proxy` (For Multi-Host Setups)

Create `/opt/dockerproxy/docker-compose.yml` on the remote VPS or managed node:

```yaml
services:
  dockerproxy:
    image: ghcr.io/tecnativa/docker-socket-proxy:latest
    container_name: dockerproxy
    restart: unless-stopped
    environment:
      # Expose only the read-only permissions required for monitoring
      - CONTAINERS=1
      - SERVICES=1
      - TASKS=1
      - POST=0
      - BUILD=0
      - COMMIT=0
      - CONFIGS=0
      - DISTRIBUTION=0
      - EXEC=0
      - IMAGES=0
      - INFO=0
      - NETWORKS=0
      - NODES=0
      - PLUGINS=0
      - SECRETS=0
      - SESSION=0
      - SWARM=0
      - SYSTEM=0
      - VOLUMES=0
    ports:
      # Recommended to expose only on LAN or WireGuard VPN subnet; if over public internet, restrict source IP with a firewall
      - "2375:2375"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
```

### 2.2 Central Server: Deploy Uptime Kuma

Create `/opt/uptime-kuma/docker-compose.yml`:

```yaml
services:
  uptime-kuma:
    image: louislam/uptime-kuma:1
    container_name: uptime-kuma
    restart: unless-stopped
    ports:
      # Direct connection default port; remove host mapping if behind NPM / Traefik
      - "3001:3001"
    volumes:
      - /opt/uptime-kuma/data:/app/data
      # Mount local socket to monitor local containers
      - /var/run/docker.sock:/var/run/docker.sock:ro
    networks:
      - monitor-net
      # Join proxy network if using a reverse proxy
      - proxy-network

networks:
  monitor-net:
    driver: bridge
  proxy-network:
    external: true
```

Start the service:

```bash
docker compose up -d
```

> [!info] Updated 2026-11-27
> `louislam/uptime-kuma:1` in the original configuration belongs to the legacy v1 branch; for fresh deployments, using the stable `louislam/uptime-kuma:2` release is recommended (if upgrading from v1, back up your data first and check the official migration notes).

## 3. Complete Telegram Alert Bot Integration Steps

### Step A: Request a Bot Token from BotFather

1. Search for the official bot `@BotFather` in Telegram.

2. Send the command `/newbot`.

3. Enter the bot's display **Name** and **Username** in order (the username must end with `bot`, e.g., `HomeLab_alert_bot`).

4. Save the returned **HTTP API Token** (format such as `123456789:ABCdefGhIJKlmNoPQRsTUVwxyZ`).

### Step B: Obtain Your Personal or Group `chat_id`

1. Search for the bot you just created in Telegram, click **Start**, or send any message to it.

2. Retrieve the Chat ID:

    - **Method 1**: Visit `https://api.telegram.org/bot<YOUR_BOT_TOKEN>/getUpdates` in a browser and locate `"chat":{"id": 123456789, ...}` in the returned JSON.

    - **Method 2**: Search for `@userinfobot` in Telegram and click Start; it will directly return your personal numeric `Id`.

### Step C: Bind the Notification Channel in Uptime Kuma

1. Open the Uptime Kuma dashboard (`http://<IP>:3001`) -> click the avatar in the top-right -> **Settings** -> **Notification** -> **Setup Notification**.

2. Select **Telegram** as the Notification Type:

    - **Bot Token**: Paste the API Token you just obtained.

    - **Chat ID**: Enter the numeric ID.

3. Click **Test**, confirm you receive the test message in Telegram, and then save.

## 4. Creating Monitors (Docker Container Monitoring)

Click "**Add New Monitor**" in the top-left:

- **Monitor local containers**:

    - **Monitor Type**: Select `Docker Container`.

    - **Docker Host**: Select the default `/var/run/docker.sock`.

    - **Container Name / ID**: Enter the target container name (e.g., `nextcloud`, `gitea`).

- **Monitor remote node containers (via Socket Proxy)**:

    1. Go to **Settings** -> **Docker Hosts** -> **Add Docker Host**.

    2. Choose `TCP Socket` as the connection type and enter `tcp://<REMOTE_VPS_IP>:2375`.

    3. When adding a monitor, switch the dropdown to that remote host, then enter the container name on that host for cross-machine monitoring.

## 5. Advanced Operations Tricks

### 5.1 "Dead Man's Switch": Passive Push Heartbeat Monitoring

Regular monitors actively ping a target, but if you want to verify whether **backup scripts, NAS jobs, or cron jobs finished on schedule**, use **Push mode**:

1. Select **"Push"** as the Monitor Type and set the heartbeat interval (e.g., 86400 seconds = 1 day).

2. Kuma generates a dedicated Webhook URL: `https://kuma.example.com/api/push/keyXYZ?status=up&msg=OK&ping=`

3. Add a check-in command at the end of your backup script:

    ```bash
    curl -fsS -m 10 --retry 3 "https://kuma.example.com/api/push/keyXYZ?status=up&msg=BackupSuccess"
    ```

- If the script crashes or hangs, Kuma will immediately trigger an alert when it fails to receive a check-in within the configured window.

### 5.2 Auto-Restart on Service Crash (Self-Healing) via Webhook

When a container goes down unexpectedly, in addition to sending a notification, you can trigger an external service to automatically recover it:

1. Add a **Webhook** under Notification settings.

2. Connect it to Node-RED or a lightweight webhook server (such as `adnanh/webhook`).

3. When a `DOWN` event is received, have the background service automatically execute `docker restart <container_name>` to achieve self-healing.

### 5.3 Built-In SSL Certificate Expiration Alerts

Select **HTTP(s)** as the Monitor Type and enter the domain name; Kuma automatically inspects the TLS certificate chain and sends alerts by default at **21, 14, and 7 days** before expiration, preventing outages caused by failed Let's Encrypt renewals.

## 6. Public Status Page and Custom CSS Glassmorphism Styling

Uptime Kuma supports creating standalone status pages so visitors can check service availability.

### 6.1 Create a Status Page

1. Click **Status Pages** in the top menu -> **New Status Page**.

2. Set the page name, slug (e.g., `/status`), and monitor groups.

3. Click **Edit** in the top-right and expand the **Custom CSS** section at the bottom.

## 7. Backup and Restore

All Uptime Kuma monitors, custom alert rules, and historical statistics are stored in `/app/data/kuma.db` (SQLite):

```bash
# 1. Back up the data directory
sudo tar -czvf /opt/backups/uptime-kuma-$(date +%F).tar.gz -C /opt/uptime-kuma data

# 2. Restore backup to a new environment
sudo tar -xzvf /opt/backups/uptime-kuma-*.tar.gz -C /opt/uptime-kuma/
docker compose restart uptime-kuma
```

> [!info] Updated 2026-11-27
> 1. Run `docker compose stop uptime-kuma` before backing up or restoring `/opt/uptime-kuma/data` to avoid data inconsistency in a running SQLite database (`kuma.db` WAL mode).
> 2. If multiple backup files exist in `/opt/backups/`, the wildcard `uptime-kuma-*.tar.gz` in the restore command will cause `tar` to fail; specify an explicit backup filename instead.
