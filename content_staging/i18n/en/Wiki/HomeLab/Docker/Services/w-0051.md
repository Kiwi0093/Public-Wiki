## 1. Architecture Concepts and Port Roles

Portainer adopts a typical Server-Agent architecture:

![](https://raw.githubusercontent.com/kiwi0093/graph/master/img/pasted-1789707250888-yk6cd8.png)

### Port Quick Reference

- **9443 (TCP)**: The default **HTTPS management interface** for modern Portainer-CE (older versions used 9000 for unencrypted HTTP; modern versions strongly recommend switching entirely to 9443).
- **9001 (TCP)**: **Portainer Agent communication port**. The agent listens on this port on managed nodes, waiting for the server to initiate connections (featuring bi-directional mTLS encryption).
- **8000 (TCP)**: **Edge Agent reverse tunnel listening port** (Edge Tunnel Server). When managed nodes are behind a NAT intranet or have firewalls strictly blocking external connections, the Edge Agent actively establishes a tunnel to the server's port 8000.

## 2. Central Deployment: Portainer-CE Server

It is recommended to manage deployment with `docker-compose.yml` for easy volume configuration, automatic restarts, and reverse proxy integration.

### Step 1: Create Dedicated Directory and Persistent Volumes

```bash
mkdir -p /opt/portainer/data
cd /opt/portainer
```

### Step 2: `docker-compose.yml` Configuration

```yaml
services:
  portainer:
    image: portainer/portainer-ce:latest
    container_name: portainer
    restart: unless-stopped
    ports:
      - "9443:9443"  # Official standard HTTPS interface
      - "8000:8000"  # Edge Agent edge tunnel (open if connecting intranet nodes is needed)
    volumes:
      - /etc/localtime:/etc/localtime:ro
      - /var/run/docker.sock:/var/run/docker.sock:ro
      - /opt/portainer/data:/data
    networks:
      - portainer-net

networks:
  portainer-net:
    driver: bridge
```

Start the service:

```bash
docker compose up -d
```

> **Security Countdown Notice**: After starting Portainer-CE for the first time, you must access `https://<Server_IP>:9443` in a browser within **5 minutes** to complete the initial administrator username and password setup. If timed out, the system will forcibly shut down to prevent unauthorized hijacking; in this case, restart the container (`docker compose restart`) to reset the timer.

## 3. Managed Node Deployment: Portainer Agent

Deploy `portainer/agent` on each VPS / node that needs to be managed.

### 3.1 `docker-compose.yml` Deployment (Managed VPS)

Create `/opt/portainer-agent/docker-compose.yml`:

```yaml
services:
  agent:
    image: portainer/agent:latest
    container_name: portainer_agent
    restart: always
    ports:
      - "9001:9001"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - /var/lib/docker/volumes:/var/lib/docker/volumes
    # Disable unnecessary privileged mode; relying solely on socket and volumes is sufficient
```

Start the Agent:

```bash
docker compose up -d
```

### 3.2 Important Mount Point Descriptions

- `/var/run/docker.sock:/var/run/docker.sock`: Allows the Agent to call the host's Docker API, reporting container operation status in real time and forwarding management commands.
- `/var/lib/docker/volumes:/var/lib/docker/volumes`: Allows the management console to directly browse, download, or upload files within volumes when clicking "Volumes" on the Web UI.

## 4. Adding Remote Nodes (Environments) in Portainer Server UI

1. Log in to the Portainer Server Web interface.
2. Click **Environments** -> **Add environment** in the left navigation bar.
3. Select **Docker Standalone** -> Click **Start Wizard**.
4. Select **Portainer Agent**:
   - **Name**: Enter an identification name (e.g., `VPS-Tokyo-01`).
   - **Environment address**: Enter the IP and port of the remote managed node in the format `<VPS_IP>:9001`.
5. Click **Connect**.
6. Once connected successfully, the remote VPS will appear in the home list. Click into it to manage containers, images, networks, and volumes on that machine just like managing the local host.

## 5. Public Network Security Hardening

Exposing Portainer and Agents on a public VPS without proper protection is equivalent to handing over root privileges of the server.

### 5.1 Strictly Limit Source IPs for Agent (Port 9001)

While `portainer/agent` has built-in connection pairing verification, it is strongly recommended to restrict access in the managed VPS firewall (`ufw` or cloud security groups) **to allow only the Portainer Server's public IP to access port 9001**:

```bash
# Execute on the managed VPS (using UFW as an example):
sudo ufw default deny incoming
sudo ufw allow ssh
# Allow only the central Server IP to access port 9001
sudo ufw allow from <PORTAINER_SERVER_IP> to any port 9001 proto tcp
sudo ufw reload
```

### 5.2 Alternative Solution for Dynamic Public IPs: Edge Agent (Active Outbound Mode)

If the managed node is behind a dynamic IP, NAT intranet, or you prefer not to expose port 9001 externally, you should use the **Edge Agent** instead:

1. Select **Edge Agent** when adding an Environment on the Server side.
2. The system will automatically generate a `docker run` command containing a key (Edge ID / Key).
3. Paste and execute it on the managed node. The managed node will actively establish a secure reverse connection to the server's `Port 8000`, requiring **zero inbound ports to be opened** on the managed node.

### 5.3 Reverse Proxy Integration (Traefik v3 / NPM)

If hosting the Server behind a reverse proxy to obtain a legitimate SSL certificate, note the following:

- **WebSocket Support**: Portainer's web terminal (Exec Console) relies on WebSockets, so the reverse proxy must maintain connection upgrading (in NPM, ensure `Websockets Support` is checked).
- **Proxy Target Port**: If NPM / Traefik and Portainer are on the same Docker network, it is recommended to reverse proxy directly to `http://portainer:9000` (if the image still supports internal HTTP) or configure ignoring self-signed certificates when proxying `https://portainer:9443`.
