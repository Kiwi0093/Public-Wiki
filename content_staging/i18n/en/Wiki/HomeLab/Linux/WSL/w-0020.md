:::tip
WSL allows users to load custom Linux Kernels by default. Because certain specific advanced applications (such as bridging networks or advanced traffic control when running QEMU/KVM virtual machines) often lack corresponding modules (like TC/QoS) in the official default kernel, compiling and configuring a custom WSL Kernel fills in these required functions.

## I. Preparation

### 1. Install Required Compilation Packages

In Arch Linux (WSL), aside from basic `base-devel`, compiling the kernel requires tools like `ncurses` (for `menuconfig`), `bc`, `flex`, `bison`, `pahole`, and `libelf`:

```bash
sudo pacman -S base-devel ncurses bc flex bison pahole libelf
```

### 2. Obtain the WSL2 Linux Kernel Source Code

Use Git to fetch Microsoft's open-source WSL Kernel source code.

> **Tip:** This assumes you want version `6.1.y`. For other versions, refer to the branch names on the GitHub repo. Appending `--depth=1` fetches only the latest commit, greatly saving download time and disk space.

```bash
git clone https://github.com/microsoft/WSL2-Linux-Kernel.git --depth=1 -b linux-msft-wsl-6.1.y
cd WSL2-Linux-Kernel
```

> [!info] Updated 2026-11-27
> Modern newer WSL2 default kernels have evolved to version `6.6.y` (branches such as `linux-msft-wsl-6.6.y`) and above; before compiling, it is recommended to check your current environment version with `uname -r`, then select the corresponding branch on [WSL2-Linux-Kernel](https://github.com/microsoft/WSL2-Linux-Kernel).

## II. Preparing the Kernel Config File

Many tutorials recommend directly copying `Microsoft/config-wsl` from the `WSL2-Linux-Kernel` repo, but **this is strongly discouraged**.

**Why avoid the official `config-wsl`?** You will find a large number of `M` (compiled as dynamically loadable modules) entries in the official file. In a WSL environment, if module paths and loading mechanisms are not specially configured, features set to `M` (such as WireGuard) will often fail to be found and will cease to work directly after replacing the custom kernel.

**Best Practice: Export Config from the Current System** — Extracting the configuration from a stably running WSL Kernel is the safest approach; extracted configuration items default to `*` (Built-in, directly bundled into the kernel).

You can use either of the following methods to export the configuration and save it as `.config` (placed in the root directory of the source code you just cloned):

```bash
zcat /proc/config.gz > .config

# or
cat /proc/config.gz | gunzip > .config
```

## III. Configuration and Compilation

### 1. Modify Config (Add TC/QoS Support)

As recommended earlier, **do not manually edit** the `.config` text file because module dependencies exist, and manual edits easily lead to errors. Use the `menuconfig` tool instead:

```bash
# If your file is named .config and located in the current directory, you can simply run make menuconfig
make menuconfig KCONFIG_CONFIG=.config
```

**Add TC/QoS (Traffic Control / Quality of Service) Support:** The reason for compiling manually this time is that the new QEMU package requires TC/QoS functionality. Once inside the text-based graphical interface, navigate to the following path and press `Y` on each item to turn them into `*` (Built-in) state: `Networking support` -> `Network options` -> `QoS and/or fair queueing`

Once configured, select `Save` and exit.

### 2. Start Compilation

After configuring and saving, you can begin compilation. We can directly specify compiling `bzImage` for greater precision:

```bash
# Compile using all CPU cores on the system (fastest)
make -j$(nproc) KCONFIG_CONFIG=.config bzImage

# Of course, if you only want to allocate a specific number of cores (e.g., 16 cores), you can specify manually:
make -j16 KCONFIG_CONFIG=.config bzImage
```

Once compilation completes, your new kernel file will reside at: `arch/x86/boot/bzImage`

## IV. Replacing and Using the Custom Kernel

Copy the compiled `bzImage` to your preferred folder on the Windows host, such as `C:\WSL_Kernel\bzImage`.

### Method A: Modify Global Setting `.wslconfig` (Strongly Recommended 🌟)

This is also the officially recommended and safest approach. Edit `C:\Users\<Your_Username>\.wslconfig` in Windows:

> **Note:** Backslashes `\` in Windows paths must be escaped as `\\` to take effect.

```ini
# Main WSL Setting Section
[wsl2]
# Allow WSL to run Hypervisor features (Required for QEMU/KVM)
nestedVirtualization=true

# Specify the custom kernel file path
kernel=C:\\WSL_Kernel\\bzImage

# Limit WSL maximum RAM usage (units can be GB/MB)
memory=16GB
```

After configuration, run `wsl --shutdown` in PowerShell to forcibly close WSL; the next time it starts, your custom kernel will be loaded (you can verify the version with `uname -r`).

### Method B: Directly Overwrite the Windows Default Kernel (Extremely Discouraged ❌)

The default path where Windows stores the WSL Kernel is: `C:\Windows\system32\lxss\tools\kernel`

> [!info] Updated 2026-11-27
> `C:\Windows\system32\lxss\tools\kernel` only applies to older WSL versions built into early Windows systems; modern WSL installed and updated via the Microsoft Store (default architecture for Windows 10/11) places kernel files in the protected `WindowsApps` directory. Please always use Method A (`.wslconfig`) to load custom kernels.

You can directly rename the compiled `bzImage` to `kernel` and drop it into this folder to overwrite it (requires administrator privileges, and WSL must be completely shut down beforehand). **Disadvantage:** Applies immediately without any configuration. **Fatal Flaw:** If your compiled kernel has a bug causing it to fail to boot, you won't even have the default rescue environment, making troubleshooting extremely difficult. Thus, this approach is extremely discouraged.
