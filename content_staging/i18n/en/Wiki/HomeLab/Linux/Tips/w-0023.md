## 1. Incident Inventory: The Long Black Screen and Ghost Windows After Login

No matter which Linux distribution you use (Arch, Fedora, Ubuntu, or openSUSE), as long as your desktop environment is **KDE Plasma 5 or Plasma 6**, after experiencing a system update, graphics driver change, or abnormal shutdown, you may occasionally encounter the following typical desktop crash symptoms:

1. **Long Black Screen Waiting After Login**: After entering your password in SDDM or GDM, the screen directly turns black and freezes for 10 to 30 seconds. The mouse pointer can move, but desktop components and the taskbar fail to appear.
2. **Forced Pop-up of Historical Windows**: Even if "Start with an empty session" is checked in system settings, every boot still forcefully restores all terminals, browsers, or specific software running before the last shutdown.
3. **Delayed Loading or Disappearance of the Panel**: After the black screen ends, the taskbar may take several seconds to emerge, or even completely fail to respond to right-click menus.

## 2. Root Cause Analysis: Why is Disabling Restoration in GUI Settings Ineffective?

KDE Plasma internally relies on `ksmserver` and `plasmashell` to manage sessions. When the system encounters a crash, display server (X11/Wayland) restart, or driver context anomaly, the status files responsible for recording window geometric states and GPU contexts easily **become corrupted or locked as read-only**.

This leads to two chain reactions:

- **GUI Switches Are Bypassed**: Although the system settings interface displays "empty session", the underlying daemon still forcibly reads the corrupted old session files.
- **Triggering the 20-Second Timeout Protection Mechanism**: When `plasmashell` boots, it frantically attempts in the background to rebuild those old windows carrying invalid GPU resources until the Session Manager's connection timeout protection mechanism is triggered, after which the desktop components tardily load.

## 3. Forceful Reset: Clearing Corrupted Sessions and Caches

Since the GUI settings have failed, the most direct and effective approach is to issue commands from the terminal to thoroughly erase corrupted status files and desktop composition caches.

1. **Erase Session Restoration Status Files**

   Configuration file paths vary slightly across Plasma versions; execute the following commands to clear both old and new specification session records together:

   ```bash
   # Delete Plasma 6 session restoration state file
   rm -f ~/.local/state/plasmasessionrestorestaterc

   # Delete Plasma 5 / 6 legacy session directory
   rm -rf ~/.config/session/*
   ```

2. **Clear Desktop Components and Window Manager Cache**

   Corrupted QML cache or KWin effect cache can similarly slow down loading speeds:

   ```bash
   # Clear temporary files for plasmashell and kwin
   rm -rf ~/.cache/plasmashell*
   rm -rf ~/.cache/kwin*
   rm -rf ~/.cache/plasma*
   ```

3. **Restart to Verify**

   After performing the above cleanup, reboot the computer or log out:

   ```bash
   systemctl reboot
   ```

   _Verification Indicator: After entering the password in SDDM, wallpapers and the taskbar should instantly load within 1 to 3 seconds, and no residual windows from the previous session should pop up._

## 4. Advanced Troubleshooting: Check Systemd User Services If Sluggishness Persists

If delays persist after clearing the cache, the problem most likely lies in background user services (Systemd User Services) that launch alongside Plasma:

```bash
# Check which user-level services slowed down the boot process during startup
systemd-analyze --user blame
```

If you find specific custom scripts or third-party synchronization tools (such as specific cloud sync software, IME daemons) taking abnormal amounts of time, you can temporarily exclude them using `systemctl --user disable <service_name>`.
