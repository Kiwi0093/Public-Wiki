# XigmaNAS SSH Service Repair and Passwordless (Public Key) Login Setup

> <img src='https://img.shields.io/badge/Status-Active-A8FF24?style=for-the-badge&labelWidth=100' height='38' />

![FreeBSD](https://img.shields.io/badge/FreeBSD-Supported-green?style=plastic&logo=freebsd) 

## 1. Fixing SSH Service Failure to Start (Error Code 1)

### Symptoms

- Starting the SSH service in the WebGUI fails with `Error Code 1`.
- Even if host keys are generated manually in the terminal (`ssh-keygen -A`), returning to the WebGUI and clicking Save causes the service to crash again immediately.

### Diagnosis

Run the following command in the console to test the SSH configuration file and force error output display:

```bash
/usr/sbin/sshd -t -f /var/etc/ssh/sshd_config 2>&1
```

If the output is `sshd: no hostkeys available -- exiting.`, it indicates that the private keys recorded in the underlying `config.xml` are corrupted or missing, causing the WebGUI to overwrite the system with incorrect keys every time settings are applied.

### Solution

You must force the system to regenerate and record new host keys via the WebGUI.

1. Go to the WebGUI and navigate to **Services -> SSH**.
2. Scroll down to find the **Private Keys** section.
3. **Clear the contents** of all four text boxes (**RSA, DSA, ECDSA, Ed25519**). *(Updated 2026-11-27: OpenSSH 10.0+ has completely removed DSA key support; newer XigmaNAS interfaces may only retain RSA, ECDSA, and Ed25519)*
4. Scroll to the bottom of the page and click **Save and Restart**.
5. Detecting the empty values, the system will automatically generate brand new host keys and write them to `config.xml`, allowing the SSH service to start normally.

## 2. Setting Up Passwordless Login (Persisting authorized_keys)

### Scenario Description

When XigmaNAS is used in **Embedded** mode, the system root directory (`/`) resides in memory (RAM Disk), which can be confirmed via `mount | grep ' / '` (`/dev/md0`). This means:

- By default, there is no `~/.ssh` directory.
- Any `/root/.ssh/authorized_keys` written via `ssh-copy-id` will disappear immediately upon reboot.

To solve this problem, you must store the public key on the physical USB boot drive (`/cf` partition) and instruct the SSH service to read that physical file directly.

### Step 1: Unlock and Write Public Key to USB Boot Drive

By default, the USB partition (`/cf`) is in Read-Only protection mode. You must first switch it to read-write mode.

1. **Mount as Read-Write:**

   ```bash
   mount -u -w /cf
   ```

2. **Create the key directory and set permissions:**

   ```bash
   mkdir -p /cf/conf/ssh_config
   chmod 700 /cf/conf/ssh_config
   ```

3. **Write the public key:** Use an editor to paste the public key of the Ansible control node or client (`id_ed25519.pub` or `zeon.key.pub`) into the file.

   ```bash
   vi /cf/conf/ssh_config/authorized_keys
   ```

4. **Set file permissions:** (Incorrect permissions will cause SSH to refuse reading the key)

   ```bash
   chmod 600 /cf/conf/ssh_config/authorized_keys
   ```

5. **Relock as Read-Only:** Protect the USB flash drive to prevent damage from frequent writes.

   ```bash
   mount -u -r /cf
   ```

### Step 2: Modify WebGUI Settings

Tell the XigmaNAS SSH service to bypass memory and read settings directly from the USB flash drive.

1. Go to the WebGUI and navigate to **Services -> SSH**.
2. Ensure **Permit root login** is checked (if root automation is required).
3. Scroll down to the **Extra options** text box.
4. Paste the following parameter:

   ```text
   AuthorizedKeysFile /cf/conf/ssh_config/authorized_keys
   ```

5. Click **Save and Restart**.

### Test Connection

Run a test from the connecting endpoint to confirm that you can log in directly without a password:

```bash
ssh -i ~/.ssh/ssh.key root@<XigmaNAS_IP>
```
