When hosting a Docusaurus-based Wiki / Blog on GitHub Pages, project sites are published by default under a subpath named after the repository (e.g., `https://kiwi0093.github.io/Public-Wiki/`).

To visit the website as a root site under an independent subdomain (such as `https://blog.kiwireich.com/`), **binding a custom domain directly to the GitHub Pages project is the most concise solution**. This approach requires no changes to the GitHub repository name (no need to rename it to `kiwi0093.github.io`) and does not affect the existing homepage, automatically mounting the project at the root path `/` of the custom domain.

---

## 1. Core Workflow and Architectural Transition

* **Before Migration**: `https://kiwi0093.github.io/Public-Wiki/` (Project site, assets and routing rely on the `/Public-Wiki/` prefix).
* **After Migration**: `https://blog.kiwireich.com/` (Independent domain site, assets and routing return to the root directory `/`).
* **Maintenance Benefits**:
  * The original repository name `Public-Wiki` (or `Public_wiki`) remains unchanged.
  * The existing `kiwi0093.github.io` repository is undisturbed, avoiding destructive relocation to `/old/`.
  * Root directory routing is naturally established, resolving cross-platform static asset referencing and hierarchical path misalignment issues.

## 2. Operation Steps

### Step A: Configure DNS CNAME Resolution Records

Log in to the DNS control panel managing your primary domain (`kiwireich.com`) (such as Cloudflare or your DNS hosting provider), and add a CNAME record for the subdomain:

| Record Type | Name / Host | Target / Value | TTL | Proxy Status (if using Cloudflare) |
| :--- | :--- | :--- | :--- | :--- |
| **CNAME** | `blog` | `kiwi0093.github.io` | Auto | **DNS only (Gray cloud)** |

> **Tip**: If your DNS is hosted on Cloudflare, it is recommended to disable the proxy (turn it into a gray cloud) during initial binding to prevent Cloudflare's edge caching and SSL termination mechanisms from interfering with GitHub's automatic Let's Encrypt certificate issuance.

---

### Step B: Modify Docusaurus Configuration (`docusaurus.config.js`)

Since the domain has changed and the path has shifted from a subdirectory to the root path, you need to calibrate the website's base URL and base path accordingly:

Edit `docusaurus.config.js` (or `docusaurus.config.ts`) in the root directory of your Wiki project:

```javascript
module.exports = {
  // Change the site main URL to the specified custom subdomain
  url: 'https://blog.kiwireich.com',

  // [Critical Fix]: Changed from original '/Public-Wiki/' to root directory '/'
  baseUrl: '/',

  // GitHub Pages deployment related declarations (keep as is)
  organizationName: 'kiwi0093',
  projectName: 'Public-Wiki',
  trailingSlash: false,

  // ... remaining theme, navbar, and plugin configurations remain unchanged ...
};
```

> [!info] Updated 2026-11-27
> The `url` field in line 3 of the original example was mistakenly written as Markdown link syntax (`'[https://blog.kiwireich.com](https://blog.kiwireich.com)'`). Please fill it in with a plain URL string `'https://blog.kiwireich.com'`, otherwise Docusaurus build will fail due to URL format validation errors:
> ```javascript
> url: 'https://blog.kiwireich.com',
> ```

### Step C: Create Static `CNAME` Declaration File (Prevent CI/CD Overwriting)

When GitHub Pages binds a custom domain, it writes a file named `CNAME` to the root of the publishing branch (such as `gh-pages`). If the project is built by automation tools like GitHub Actions, every build overwrites the publishing branch with `./build`, causing the domain configured manually in web settings to be overwritten and cleared.

Include `CNAME` in Docusaurus's static asset directory (`static/`), and the build process will automatically copy it to the output root directory:

1. Create a file named `static/CNAME` (note: no file extension) under the project's `static/` folder.
2. The content should only contain a single line with your custom domain name:

```text
blog.kiwireich.com
```

### Step D: Push Changes and Trigger GitHub Actions

Commit and push your settings and static files to GitHub:

```bash
git add docusaurus.config.js static/CNAME
git commit -m "feat: configure custom domain blog.kiwireich.com and set baseUrl to root"
git push origin main
```

After pushing, check the **Actions** tab of your GitHub repository to ensure the automated deployment workflow completes successfully.

### Step E: Confirm in GitHub Repository Settings and Enforce HTTPS

1. Open the `Public-Wiki` repository on GitHub.
2. Click **Settings** ➔ **Pages** in the left sidebar.
3. Check the **Custom domain** field:
   - The system should now automatically populate `blog.kiwireich.com` (if not, enter it manually and click **Save**).
4. **DNS Verification and Certificate Issuance**:
   - The system will automatically perform a **DNS check**. Once passed, GitHub will request a TLS/SSL certificate for the domain (usually takes about 5 to 15 minutes).
5. Once certificate issuance is complete, check **Enforce HTTPS** to ensure all unencrypted HTTP traffic is automatically redirected to HTTPS.

## 3. Verification Checklist

- [ ] Open `https://blog.kiwireich.com/` in a browser and verify that the homepage loads normally without layout breakage.
- [ ] Check loading paths of CSS, JS, and image assets, confirming they all start with `https://blog.kiwireich.com/assets/...` rather than the old `/Public-Wiki/` path.
- [ ] Check internal cross-page links in Wiki and Blog to confirm route switching has no 404 errors.
- [ ] Check SSL certificate status to ensure the browser address bar displays a secure encryption padlock indicator.
