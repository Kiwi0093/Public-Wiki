# Red Hat Stops Publishing Source Code for Downstream Rebuilds

## Personal Take

As a commercial distribution (and one that charges money), using licensing and withholding direct access to `source code` to protect its commercial value is completely normal. `SUSE`'s commercial edition (SLES) doesn't hand out `Source code` for direct downstream rebuilds either.

Moreover, both of them have their own upstream `open source` editions:

| | Red Hat | SUSE |
| -------------- | ------------------------ | --------------------- |
| Open Source Upstream | Fedora / CentOS stream | OpenSuSE |
| Commercial Edition | Red Hat Enterprise Linux | SUSE Linux Enterprise |

The ones getting killed off right now are `RHEL` downstream clones. Thinking about it, it makes sense—the company developing it needs to make money, and developers need to put food on the table.

As for all the "they broke promises they made before the company took off" drama, well—people get divorced even after getting married, and vows sworn before the gods get ignored all the time...

As for SUSE and Oracle jumping out right now to ride the wave, I think they're mostly seizing the opportunity to kick Red Hat while the sentiment is hot, seeing if public opinion can sway some frustrated Red Hat users into switching to their own paid distros. Let's grab some popcorn and watch how this plays out.

# NixOS

Recently, NixOS suddenly blew up among Linux YouTubers for some reason, so I hopped on the bandwagon and gave it a try too.

## Hands-on Impressions

Honestly, the moment I touched it, the shock was pretty similar to the first time I installed `Gentoo`, and my takeaway was pretty much the same—basically:

> Whoa~ this thing's special features are so cool~ I can do this, and I can do that too~~

Then, after cooling down and thinking about it: sure, you *can* use it, though it's quite a hassle, and you don't really *have* to use it either.

There's no compelling reason that makes it strictly indispensable...

### Strengths

`NixOS` is basically a dedicated OS owned by a package manager... (a bit like Prussia in a certain era—other countries have an army, while Prussia was an army that had a country).

The core of `NixOS` is the `Nix` package manager, so it can configure the entire system using a single (or multiple importable) `.nix` configuration file (well, in theory—user configs in `~/.config` still behave like usual). And every time you update, add, or remove a package, it rebuilds system symlinks so each `version` is isolated, and you can even spin up separate profile dev environments without touching the host system.

Sounds super cool and awesome, right?

### Drawbacks

Something that sounds this flashy is bound to have corresponding drawbacks that haven't been solved (equivalent exchange, after all). After playing around with it briefly, I noticed:

* To make permanent system changes, you *have* to edit `/etc/nixos/configure.nix` and run `nixos-rebuild switch` to update the whole system generation.

* The system itself has major release versions and `channel`s. And to fully achieve the "one config file to rule them all" ideal, they introduced something called `flake`... making it even more convoluted. Honestly, going rolling-release from the start would have been simpler...

* Huge disk space requirements. While you can use `nix-garbage-collection` to delete generations outside a certain range, doing so kinda defeats the whole point of the rollback features its fans brag about—if you wipe all your snapshots, what are you supposed to roll back to??

### Mini-Conclusion

It's pretty great for tinkering, or if you have a huge fleet of identical machines to deploy and manage—assuming you don't constantly tweak the system, or you have a dedicated test machine to dial in the config before applying it everywhere.

As a daily-driver desktop OS, it's probably not ideal...

Unless you really need multiple dev environments coexisting on one system without interfering with each other *and* you also deeply despise container tech like Docker...

# ArchInstall

Earlier, I saw some YouTubers talking about a new tool in `Archlinux` that makes installation friendlier for newcomers.

I ignored it for a long time until I finally tested it myself recently—and wow, it blew me away.

I've written my own install scripts before, and I'm sure lots of Arch users have written their own too.

The only pity is I haven't figured out how to customize its default profile yet...

# NeoVim+Nvchad

I actually ended up messing with this again because I couldn't resist tinkering while testing `NixOS` (otherwise I hadn't touched it in ages).

Just a few key takeaways:

* On Arch-based Linux, please do **not** install `NvChad` from the `AUR`—it causes errors. Just do a clean `git clone` like a good citizen.

* The default keybindings in the newer version are actually pretty nice; you barely need to remap anything manually, and `<leader>+ch` lets you view the hotkey `cheat sheet`.

* I still haven't sorted out the LSP and formatting setup yet—I'll find time to look into it later...
