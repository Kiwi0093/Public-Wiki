## Limitations of Ansible

Even though Ansible is powerful and makes everything look awesome, it still has these limitations (for me):

* There is no interactive manual input during execution—everything has to be written out in advance. If you host it on a public Git server like `GitHub`, security concerns come up.

* Behavioral differences are defined via Host Vars, while non-repetitive actions are controlled by separate playbook sections. Combined with the point above, it doesn't feel great for initial server setup right after installation.

* It operates over an SSH account, so similarly, on a freshly installed machine without an account and corresponding SSH key set up yet, you can't use it right away.

## Kiwi-Style Workflow

* Handle general initial setup through a `shell script`, keeping interactive prompt options so the script stays versatile.

* Paired with scripts, use Ansible mainly for highly repetitive, homogeneous tasks—for example, keeping all servers updated in sync, and version-controlling config files across all servers through Ansible (since Ansible is typically used alongside a Git server).

* Use Ansible to automatically provision environments that require complex setup—such as multiple desktops, or simplifying the work when reinstalling a desktop (while a script can do this too, scripts have a harder time managing version control for individual config files).

# Implementation

Taking a closer look at what I'm currently working on, aside from machines that aren't on the internal network where `ansible` comes in handy, pretty much everything else can already be handled with an internal `Git server` + `shell script` (to some extent, even the `rsync` + `shell script` approach I originally wanted would have been enough....).
