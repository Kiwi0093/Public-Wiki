壁越えツール（梯子）とその周辺

2020年11月27日 · 約11分
備考

備考

この記事は旧サイトのアーカイブから転載したものです。

一昨日、また格安の VPS を 1 台手に入れました。RackNerd の感謝祭セールで、2 年間の利用権を 18 USD 前後で契約しました。

VLESS​

今回の購入は主に VLESS の設定と使用感を検証するためのものなので、環境を手に入れてすぐ VLESS を導入しました。詳細なインストールメモは例によって Wiki の方にまとめる予定なので、ここではインストールや設定の細かい手順には触れず、使ってみた初期の感想を書いていこうと思います。

動機​

VLESS が登場した背景には VMess の問題（100% 検知されてしまう点）があると知ってはいますが、手元にあるプロキシ環境はすべて WS+TLS 構成にしているので、実はそこまで危険ではありません（そもそもそれで危険だと言うなら VLESS も同じように危険なはず……）。そのため絶対に VLESS に乗り換える必要があったわけではないのですが、中国本土のユーザーたちのおすすめ記事を見ていると、VLESS は効率がかなり良くなっているらしく（従来の VMess にあった暗号化や認証などを取り除いているので、理論上速くなるのは当然ですが）。

つい我慢できなくなってしまって……（衝動買いの典型です）。

違い​

VMess+WS+TLS を使う場合は面倒なので、基本的に WS+TLS 周りの処理は Caddy に任せる構成をおすすめしていました。しかし VLESS の設定では TLS を V2Ray 内部に組み込む必要があるため、SSL Key の場所を指定しなければなりません。その結果、Caddy の便利だった自動 SSL 証明書処理の部分がかえってひと手間になってしまいます（厳密には問題というほどではなく、自動処理ゆえに Key がどこに保存されているか自分で探して確認しないといけないというだけですが）。さらに Caddy v2 の設定ファイルは v1 と比べて複雑になり、設定ロジックや参考資料も Nginx や Apache ほど馴染みがありません（結局のところ、自分のスキル不足に起因するわけですが……）。

検証環境​

Caddy が不要になったので、妙なこだわりを持つ私は、アンインストールなどの作業をする代わりにシステム全体を再インストールしたくなります（ある意味 VM に甘やかされた癖ですね、大きく変更するのが面倒なときは再インストールで済ませてしまうという）。そこで最初は自宅にあるバックアップ用 V2Ray を動かしている Arch Linux マシンから手を付けました。ちょうど最近 Arch Linux の自動インストールスクリプトを書き直していたこともあり、つい熱が入って再インストールしながらスクリプトのデバッグを進めていました（ここで言わせてもらうと、インストール手順がまた少し変わったせいでスクリプトのコア部分を書き直す羽目になり、かなり面倒でした……）。そのため一昨日はほとんどの時間をスクリプトの調整と OS の再インストールに費やしました……。

その後 RackNerd を契約したので、ちょうど良い機会だと思ってそのまま試すことにしました。ただ、こうした VPS は基本的に Debian/Ubuntu 系や CentOS 系の OS しかなく、私が好んで使っている Arch Linux がありません……。

ネット上のチュートリアルをいくつか見てみると、やはり Arch Linux を使った方がシンプルに済みそうな印象を受けます。少なくとも pacman だけでインストールが完結し、別途スクリプトを走らせる必要も、自動更新のために crontab を書き換える必要もありません（そういえば、スクリプトのパスを変更したせいで、他の VPS の自動更新はほぼ全滅してしまいました）。

サーバー側の感想​

V2Ray 自体で WS+TLS の処理ができるため、最初は単純に「インストール時に Nginx や Apache を入れなくてもいいのでは」と思っていましたが、よく考えてみると Certbot での SSL Key 管理をするには入れておいた方が楽なので、結局インストールしました……。

ただ全体として見れば、V2Ray の設定さえ済ませてしまえば Nginx/Apache を起動しなくても WS 機能を動かせるのはかなり気楽です。Web サーバーの設定を 1 つ減らせるわけですから。もっとも結論としては、Web サーバーの設定もしておかないと fallback 周りで問題が起きる可能性が高そうですが。

こうした流れを見ていると、V2Ray チームの方向性がよく分かります。最初から V2Ray は単なる SOCKS サーバーにとどまるつもりはなく、高い拡張性を備えた総合ネットワーク管理ツールを目指しているようです。内部に DNS、Routing Table、通信プロトコルや暗号化機能などを備えており、そのうち単なる WS 機能だけでなく Web サーバーの完全なモジュールまで取り込まれても、私はまったく驚かないでしょう。

現在はテンプレートに沿って最小構成で VLESS+WS+TLS を設定してあります。今後 XTLS のライセンス問題が解決したら、本当にそんなにすごいのか（「素通しと同じくらい速い」とまで言われていますが……）VLESS+XTLS も試してみるかもしれません。

クライアント側の感想​

Gateway V2Ray クライアント​

はい、部屋の Gateway の接続先を VLESS+WS+TLS が動いているこの VPS に切り替えました。今のところ普通に動作していますが、速度については中国聯通（China Unicom）の貧弱な回線がボトルネックになっているため、速くなったかどうかまったく分かりません……（つまり最初の動機はまるで達成できていないわけですが、まあ良い回線もないのに速度や効率を気にする方がお門違いですよね？？）。

現在は安定性テストの段階という位置づけで、今後数日間使ってみて何かサプライズがあるか（変なトラブルでなければ良いのですが）様子を見ています。

Linux クライアント - QV2Ray + V2Ray​

私の Linux デスクトップ（今このブログを書いているマシン）は Manjaro なので、Arch チームのおかげで V2Ray をとても簡単にインストールできます。

使ってみた感想としては……まあ、ほんの少し試しただけですぐやめてしまいました。主な理由は、今のオフィスに繋げる Wi-Fi がないためです（なのでこの記事も書いた当日に時間通り公開することはできないでしょう）。

ただ動かした感じでは Gateway とほぼ変わらない状態で、ほとんど差はなく、やはり回線側の制約を受けているようです。

Android クライアント - V2RayNG​

現時点で VLESS に対応しているクライアントがまだ多くないため、スマホに新しく V2RayNG をインストールすることにしました。正直なところ、BifrostV より安定していて使いやすいと感じます。実はこの記事も、主にこのアプリの話をしたくて書き始めたようなものです（ということは今までの前置きは全部無駄話！？）。

メリット（非常に主観的）​

  • QR コード（Barcode）が QV2Ray と共通

    まず、このアプリが対応している QR コードの形式が Qv2ray と同じ「標準規格」である点です。独自規格の QR コードを使う BifrostV と比べると使い勝手がかなり良いです。もっともこれは BifrostV が頑固というわけではなく、以前は V2Ray の接続用 QR コードの規格が明確に定義されていなかったためなのですが、いずれにせよ同じ規格の QR コードが使えるのはやはり便利です。

  • 広告がなく、UI が好み

    無料アプリに広告が出ること自体はそこまで抵抗があるわけではないのですが、アプリ内がすっきりしていて余計な広告がないとやはり気分が良いものです。

    以前使っていた Shadowsocks というアプリにとても良い印象を持っていたからかもしれません。シンプルな UI デザイン、レスポンスの速さ、そして初めて安定して壁越えできたという原体験もあり、Shadowsocks にそっくりなインターフェースを持つ V2RayNG に対してかなり高い好感度を抱いています。

  • アプリの反応が速く、安定性が高い

    V2Ray を使うために最初 BifrostV に乗り換えたとき、このアプリは反応や安定性が Shadowsocks に及ばないと感じることがよくありました。開いても反応しなかったり、繋いでいる途中で原因不明の切断が起きたりといった問題が頻繁に発生していたのです。ただ当時はこれほど多くのプロトコルをカバーできる代替アプリがないと思っていたため、ずっと我慢して使い続けていました。そして今回 VLESS のために V2RayNG へ乗り換えた瞬間、世界が変わりました……。

    あの頃の Shadowsocks を使っていた感覚が戻ってきた気がします。もっとも、おっさん（私）はそもそもあまり外を出歩かないので、スマホやタブレット単体での壁越えをそこまでヘビーに使うわけではありませんし、部屋に戻れば自宅の Wi-Fi 自体がすでに壁越え済みの Gateway 配下にあるので、二重にプロキシを通すこともないのですが……。

デメリット​

  • DNS の問題

    VLESS 側の問題なのか V2RayNG 側の問題なのかは分かりませんが、DNS 汚染への対処があまりうまく機能していないようです。同じ設定で VMess+WS+TLS に接続すると普通に使えるのに、VLESS+WS+TLS に繋いだ途端に DNS 異常が起きて接続できなくなります。適当にいろいろ試した結果、以下の設定にしたときだけ正常に使えるようになりました。

    • ドメイン戦略（Domain Strategy） - IPIfNonMatch でも IPOnDemand でも可
    • 事前定義ルール（Predefined Rules） - LAN および中国本土をバイパス
    • ローカル DNS を有効にする（Enable Local DNS） - 絶対に有効にしない
    • リモート DNS（Remote DNS） - Google の 8.8.8.8 に変更

    今のところこれで動いていますが、どう考えても問題が起きるはずのない部分なので、今後原因が見えてきたらまた更新しようと思います。

まとめ​

とにかく、「梯子（壁越えツール）」に関する技術というのは、世界中を見渡しても某大国天朝にいる人くらいしか習得しようとしない技術です。私の師匠が言っていた「すごくニッチなスキルツリーだよね。このメンバーの中でそこにポイントを振るのは、現地駐在している君くらいだろう」という言葉の通り、私もネット上の資料を漁ってほんの上澄みだけを学び、ここで恥ずかしながら披露しているにすぎません。

それでも幸いなことに、天朝には志ある有志がたくさんいるので、関連資料自体はわりと簡単に見つかります。そう……壁の外に出て Google で検索すればすぐ見つかるのですが、壁の内側の世界では 1 記事も見つかりません……。

結局のところ「梯子」なんてものは、最初に 1 回だけ外へ出るための道具さえあれば、あとはどんな風に次の梯子を組むにしても比較的楽になるものなのです……。

とはいえ、梯子を組むという行為は本来、天朝の国家システムに対してささやかな抵抗を試みるようなものなので、常にアップデートと改善を続けなければなりません。本当に一度きりで永久に解決したいのであれば、

やはり「肉身翻牆（物理的に国外へ出ること）」か「物理的な壁越え」が一番確実ですね。
