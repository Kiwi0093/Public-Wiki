Gitea 軽量セルフホスト Git サーバー構築・運用マニュアル (Wiki)

1. アーキテクチャの位置づけと主要設計方針​

HomeLab 内部の自動化（Ansible / Docusaurus / Docker Compose Repo など）に特化した環境において、この構成には以下の設計上の重点があります。

  • 内部ネットワーク専用 HTTP ポリシー：

    隔離された内部ネットワーク内では、Git サーバーは内部の VM や物理ノードがコードを取得する用途（例：ansible-pull -U http://git.internal.local/admin/homelab.git）にのみ使用されます。内部 HTTP を採用することで、内部 CA の自己署名証明書の期限切れや、各クライアントノードへの Root CA の手動インストールといった管理の手間を完全に省けます。

  • データベース選定：なぜ SQLite を避けて MySQL / MariaDB を採用するのか？

    • SQLite は本質的に単一ファイルデータベースであり、高頻度の同時書き込みが発生するとテーブル全体／データベースレベルのロック（Database-level Lock）が発動します。
    • 複数ノードが同時に ansible-pull を実行したり、複数の Git Hook / CI Runner が同時にステータスを報告したりすると、database is locked (5) という致命的エラーが頻発し、Git Push/Pull が失敗・中断してしまいます。
    • 独立した MySQL / MariaDB を採用することで、行レベルロック（Row-level Lock）とコネクションプールによってロックタイムアウトの問題を根本から解消できます。

  • SSH ポート競合の回避：

    コンテナ内で SSH プロトコル経由の Git（git@host:repo.git）を公開したい場合、コンテナ内の Port 22 をホストマシンの 22 番に直接マッピングすることは厳禁です（ホスト自身の SSH 管理ポートと競合するため）。通常は 2222:22 のようにマッピングするか、ホスト側の OpenSSH の AuthorizedKeysCommand を通じてパススルーを実現します。 あるいは Macvlan を採用して独立した IP を割り当て、SSH 用のドメインをその IP に向ければポートマッピング自体が不要になりますが、その場合は HTTP と SSH で異なるドメイン名へ接続することになります。

2. Docker Compose 完全デプロイテンプレート​

手順 1：専用ディレクトリと権限の作成​

sudo mkdir -p /opt/gitea/data /opt/gitea/config /opt/gitea/mysql
# Gitea 公式イメージはデフォルトで UID 1000 で動作します
sudo chown -R 1000:1000 /opt/gitea/data /opt/gitea/config

手順 2：docker-compose.yml の設定​

/opt/gitea/docker-compose.yml に以下を記述します。

services:
  server:
    image: gitea/gitea:latest
    container_name: gitea
    restart: unless-stopped
    depends_on:
      db:
        condition: service_healthy
    environment:
      - USER_UID=1000
      - USER_GID=1000
      - TZ=Asia/Taipei
      # 重要：外部アクセス URL（Web UI で Git Clone リンクをコピーする際の生成パスに影響）
      - GITEA__server__ROOT_URL=http://git.internal.local/
      - GITEA__server__HTTP_PORT=3000
      - GITEA__server__DOMAIN=git.internal.local
      - GITEA__server__SSH_PORT=2222
      - GITEA__server__SSH_LISTEN_PORT=22
      # データベース接続設定（GITEA__*__* 形式で app.ini を自動上書き可能）
      - GITEA__database__DB_TYPE=mysql
      - GITEA__database__HOST=db:3306
      - GITEA__database__NAME=gitea
      - GITEA__database__USER=gitea
      - GITEA__database__PASSWD=gitea_secret_password
    volumes:
      - /opt/gitea/data:/data
      - /opt/gitea/config:/etc/gitea
      - /etc/timezone:/etc/timezone:ro
      - /etc/localtime:/etc/localtime:ro
    ports:
      # Git SSH サービスポート（外部アクセスは 2222 を使用）
      - "2222:22"
      # NPM リバースプロキシ経由かつ同一 Docker ネットワーク内であれば、以下の 3000 番ポートの外部マッピング自体も不要
      - "3000:3000"
    networks:
      - backend

  db:
    image: mariadb:10.11
    container_name: gitea_db
    restart: unless-stopped
    command:
      - "mariadbd"
      - "--character-set-server=utf8mb4"
      - "--collation-server=utf8mb4_unicode_ci"
      - "--innodb-file-per-table=1"
    environment:
      - TZ=Asia/Taipei
      - MARIADB_ROOT_PASSWORD=db_root_secret_password
      - MARIADB_DATABASE=gitea
      - MARIADB_USER=gitea
      - MARIADB_PASSWORD=gitea_secret_password
    volumes:
      - /opt/gitea/mysql:/var/lib/mysql
    networks:
      - backend
    healthcheck:
      test: ["CMD", "healthcheck.sh", "--connect", "--innodb_initialized"]
      interval: 5s
      timeout: 5s
      retries: 10

networks:
  backend:
    driver: bridge
    # 共用の npm-network を使用している場合は外部ネットワークをそのままマウント可能：
    # external: true
    # name: npm-network

改善ポイント：

  1. 以前は mysql:latest の使用時にデフォルト認証プラグインの変更（caching_sha2_password など）による接続断が発生することがあったため、ここでは長期サポート版の mariadb:10.11 を推奨しています。リソース消費が抑えられ、互換性も良好です。
  2. healthcheck と depends_on: condition: service_healthy を追加することで、データベースの初期化完了後に Gitea サービスが起動するようになり、起動直後の DB Connection Refused エラーを完全に防ぎます。

3. リバースプロキシ連携 (Nginx Proxy Manager)​

NPM と Gitea を同じカスタムネットワーク（例えば backend や外部共用の npm-network）に接続すると、リバースプロキシの設定は非常にシンプルになります。

NPM Proxy Host 設定​

  1. Hosts -> Proxy Hosts -> Add Proxy Host に移動します。

  2. Details タブの設定：

    • Domain Names：git.internal.local
    • Scheme：http
    • Forward Hostname / IP：gitea（コンテナ名をそのまま入力）
    • Forward Port：3000（Gitea コンテナ内部のデフォルト Listen ポート）
    • Websockets Support にチェックを入れます（Gitea 内部通知に必要）。

  3. 大容量ファイルアップロード時の中断防止 (重要)：

    • Advanced タブへ移動し、カスタム Nginx 設定欄に以下を貼り付けます：
    # 大容量の Git Push を許可（デフォルトは 1MB のみで、大きなプロジェクトやバイナリファイルが弾かれます）
    client_max_body_size 512M;

4. Ansible-Pull との組み合わせ実践テクニック​

HomeLab で ansible-pull を利用してノードの自己構成を行う際、Gitea の純粋な HTTP 構成の利点が特に際立ちます。

4.1 パスワードレス読み取り専用アカウントまたは Access Token の作成​

  1. Gitea 上に自動運用専用のアカウント（例：ci-bot）を作成します。
  2. そのアカウントの 設定 -> アプリケーション から、read:repository 権限を持つ 個人アクセストークン (Personal Access Token) を発行します。

4.2 ノード側での ansible-pull 実行​

クライアントホストで自動同期を実行します（SSH Key の配置や証明書の信頼設定は不要です）。

# Token を使用した純粋な HTTP によるプルおよび実行
ansible-pull -U http://ci-bot:<YOUR_TOKEN>@git.internal.local/infra/homelab-ansible.git \
  -i localhost, \
  local.yml

5. よくあるハマりポイントとトラブルシューティング (Troubleshooting)​

異常現象根本原因対処手順
Git Push エラー：RPC failed; HTTP 413 curl 22 The requested URL returned error: 413NPM 経由時に Nginx デフォルトの client_max_body_size 制限に引っかかっているNPM の Advanced 設定に client_max_body_size 512M;（またはそれ以上）を追加し、Gitea の app.ini の [repository.upload] FILE_MAX_SIZE = 512 も確認する。
Web UI で Clone をクリックしてコピーされる URL が http://localhost:3000/... になるROOT_URL が正しく解決されていない環境変数に GITEA__server__ROOT_URL=http://git.internal.local/（末尾に必ずスラッシュ / を付与）が設定されているか確認し、コンテナを再起動する。
SSH 経由の Clone が失敗する（Permission denied / Connection refused）外部ポートマッピングの指定ミス、またはホストとコンテナの SSH の混同1. 接続時にポート 2222 を指定しているか確認：git clone ssh://git@git.internal.local:2222/user/repo.git。
2. 毎回 2222 を打ちたくない場合は、クライアントの ~/.ssh/config にエイリアスを定義する。
管理者パスワードを忘れたWeb UI からログインしてリセットできないコンテナ内の CLI を使ってワンコマンドで管理者パスワードをリセット：
docker compose exec --user 1000 server gitea admin user change-password --username admin --password "New_Password"

6. データバックアップと災害復旧​

Gitea 公式では専用のバックアップコマンドが提供されており、データベースの SQL、リポジトリのベアリポジトリ（Bare Repositories）、ユーザー設定、プラグインデータを単一の ZIP アーカイブにまとめて出力できます。

# 1. コンテナ内でワンコマンドバックアップを実行
docker compose exec -T --user 1000 server gitea dump -c /data/gitea/conf/app.ini --file /data/gitea-dump.zip

# 2. バックアップファイルをホストのディレクトリからバックアップ保存先へ移動
sudo mv /opt/gitea/data/gitea-dump.zip /opt/backups/gitea-$(date +%F).zip

# 復元方法（新規のクリーンなディレクトリにて）：
# unzip gitea-dump.zip
# 展開された SQL を MariaDB にインポートし、data ディレクトリを /opt/gitea/data/gitea に上書き復元する
注記

実際に gitea dump を実行する際は、コンテナ内のマウントおよび環境変数設定に応じて、-c に指定する app.ini のパスが /etc/gitea/app.ini か /data/gitea/conf/app.ini かを確認してください。
