Nginx Proxy Manager (NPM) の構築、内部転送およびメンテナンス

1. データベースの選定：SQLite vs. MariaDB​

NPM は内部で Proxy Hosts、Redirection、ユーザーアカウント情報などを保存します。

  • SQLite（強く推奨）：新バージョンの NPM ではデフォルトで SQLite が組み込まれています。複数台による負荷分散やクラスター構成が不要であれば、SQLite をそのまま使うことで外部 RDB への依存を完全になくし、メモリ消費の節約と運用管理の大幅な簡素化を実現できます。

  • MariaDB / MySQL：すでに共有 DB 環境（LibreNMS や WordPress 用の共用 DB など）がある場合や、高可用性要件が厳しい場合は、環境変数によって切り替えることも可能です。

2. Docker Compose による構築（SQLite 軽量構成）​

独立した共有の Docker ネットワーク（例：npm-network）を作成しておくと、他のバックエンドコンテナを同じネットワークに参加させるだけでコンテナ名（Container Name）による名前解決・通信が可能になり、ホスト側への物理ポートマッピング（Port Mapping）が一切不要になります。

ステップ 1：事前ディレクトリと専用ネットワークの作成​

# 共有ネットワークを作成（未作成の場合）
docker network create npm-network

# 永続化ディレクトリを作成
mkdir -p /opt/npm/data
mkdir -p /opt/npm/letsencrypt

ステップ 2：docker-compose.yml の設定​

/opt/npm/docker-compose.yml に以下を定義します。

services:
  npm:
    image: jc21/nginx-proxy-manager:latest
    container_name: nginx-proxy-manager
    restart: unless-stopped
    ports:
      - "80:80"      # HTTP 転送および ACME チャレンジ
      - "81:81"      # Web 管理ダッシュボード
      - "443:443"    # HTTPS 転送
    volumes:
      - /opt/npm/data:/data
      - /opt/npm/letsencrypt:/etc/letsencrypt
    networks:
      - npm-network

networks:
  npm-network:
    external: true

サービスを起動します。

docker compose up -d

3. 初期設定とログイン​

  1. ブラウザで http://<Host_IP>:81 にアクセスします。

  2. デフォルトアカウントとパスワード：Email: admin@example.com / Password: changeme (Updated 2026-11-27: 新バージョンの NPM では初回 WebUI アクセス時に管理者アカウントの作成画面が表示されるようになり、このデフォルト認証情報は廃止されました。旧バージョンのみデフォルト認証情報でログインし、初回ログイン後に変更を求められます)

    • Email：admin@example.com

    • Password：changeme

  3. 初回ログイン後、システムにより管理者名、Email、パスワードの変更が強制されるため、新しいパスワードを安全に保管してください。

4. アーキテクチャの要：コンテナ名による内部転送（Zero-Port Mapping）​

外部へのサービス公開だけでなく、LAN 内環境（AdGuard Home、Pi-hole、Unbound などの内部 DNS と併用）において最もスマートな NPM の使い方は、「Container Name」を直接転送先として指定することです。

基本的な動作仕組み​

  1. 同一の Docker Network：Docker には組み込みの Embedded DNS Server（127.0.0.11）があるため、2つのコンテナが同じカスタム bridge ネットワーク（例：npm-network）に所属していれば、コンテナ名から互いの内部 IP を直接名前解決できます。

  2. バックエンドコンテナのポート公開が不要：バックエンドコンテナ（Emby、Jellyfin、Vaultwarden など）は、ports: でホスト側にポートを公開する必要が一切なく、コンテナ内部で待受ポートを開くだけで済みます。これによりホストのポート競合を防げるだけでなく、LAN 内の攻撃対象領域（Attack Surface）を大幅に減らせます。

バックエンドアプリ（Emby を例とした）設定例​

services:
  emby:
    image: amir20/clash # または任意のイメージ（ここでは emby を例示）
    container_name: emby
    restart: unless-stopped
    # ポイント：ports: - "8096:8096" の記述は一切不要
    networks:
      - npm-network

networks:
  npm-network:
    external: true
Updated 2026-11-27

上記の例にある image: amir20/clash は誤記です（amir20 は Dozzle の開発者であり、Clash もメディアサーバーではありません）。実際に Emby をデプロイする際は、公式イメージ emby/embyserver:latest または lscr.io/linuxserver/emby:latest を使用してください。

NPM Web UI 設定（Proxy Host）​

  1. Hosts -> Proxy Hosts -> Add Proxy Host に進みます。

  2. Details タブに以下を入力します。

    • Domain Names：emby.internal.local（内部 DNS で NPM ホストの IP に向けておく）

    • Scheme：http

    • Forward Hostname / IP：emby（コンテナ名を直接入力）

    • Forward Port：8096（対象コンテナ内部の待受ポートを入力）

    • Block Common Exploits および（リアルタイム通信が必要なアプリであれば）Websockets Support にチェックを入れます。

5. 証明書管理：カスタム証明書（Custom SSL）と Let's Encrypt​

NPM では UI から Let's Encrypt 経由で新規発行するしかないと思われがちですが、実際にはローカルに既存の証明書をインポートする機能（Custom Certificates）も完全にサポートしています。

5.1 既存証明書／ワイルドカード証明書のインポート（Custom Certificate）​

すでにホスト側や acme.sh / DNS API などで証明書を取得している場合：

  1. SSL Certificates -> Add SSL Certificate を開き、Custom を選択します。

  2. 証明書名（例：My-Wildcard-Cert）を入力します。

  3. ファイルをアップロードまたは貼り付けます。

    • Certificate Key：秘密鍵の内容（*.key）。

    • Certificate：完全な証明書チェーン（fullchain.pem、または証明書本体と中間 CA を含むファイル）。

  4. 保存後、各 Proxy Host の SSL タブのドロップダウンからそのカスタム証明書をそのまま選択できます。

5.2 NPM から Let's Encrypt 証明書を自動取得する​

  • HTTP-01 チャレンジ：ドメイン名を入力して取得します。ホストのポート 80 へインターネットから到達可能である必要があります。

  • DNS-01 チャレンジ（ワイルドカード証明書向け推奨）：Use a DNS Challenge にチェックを入れ、利用中の DNS プロバイダー（Cloudflare など）を選択して API Token を入力すれば、*.example.com のワイルドカード証明書を自動発行できます。

6. よくあるハマりポイントとトラブルシューティング (Troubleshooting)​

6.1 Calibre-Web が Subpath / Reverse Proxy 下で表示崩れやリダイレクト不良を起こす​

Calibre-Web などのアプリは、リバースプロキシのヘッダーや Script Name の扱いにシビアです。解決策：NPM の該当 Host 設定にある Custom Locations から対象パスを追加し、右側の歯車アイコン（詳細設定）をクリックして以下の Nginx ヘッダー設定を追記します。

proxy_bind $server_addr;
proxy_set_header Host $http_host;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Scheme $scheme;
proxy_set_header X-Script-Name /${your_location};

6.2 Portainer-CE を Sub-location（サブパス）で運用する際の注意点​

  • 原因：Portainer-CE のフロントエンド（Angular/Vue）はアセットのパスをルート / 基準の絶対パスで参照しているため、/portainer のようなサブパス配下に無理やり押し込むと JS/CSS の 404 エラーが大量発生してレイアウトが崩れ、さらに WebSocket（/api/websocket/...）接続も切断されやすくなります。

  • ベストプラクティス：サブパスは使わず、必ず独立したサブドメイン（Subdomain）を Virtual Host として割り当てることを強く推奨します（例：portainer.internal.local）。

  • 重要設定：Portainer をリバースプロキシする際は、NPM 側で必ず Websockets Support を有効にしてください。有効にしないと Web コンソール（Console / Exec）が即座に切断されます。

6.3 ルート（Host /）のポータル画面化​

NPM に向けたドメイン名でどの Proxy Host にも一致しない場合、NPM 標準の「Congratulations」ページが表示されます。

  • 活用テクニック：Homepage、Dashy、Heimdall などのダッシュボードコンテナを立てておき、NPM 上でフォールバック用またはメインドメインの Proxy Host をそのダッシュボードコンテナへ向けることで、HomeLab 全体のポータル・ランチャー画面として活用できます。

7. Traefik vs. Nginx Proxy Manager 選定早見表​

比較項目Nginx Proxy Manager (NPM)Traefik (v3)
主な位置づけGUI ベース管理、直感的操作、従来型 Nginx の拡張クラウドネイティブ、宣言的設定、マイクロサービス向けエッジルーター
設定の入り口Web UI（DB に保存）Docker Labels または静的/動的 YAML/TOML
自動検出UI から手動で Host と Port を追加する必要ありdocker.sock を自動監視し、コンテナ起動と同時にルーティング反映
外部の非 Docker サービス非常に扱いやすい（UI に物理マシンの IP:Port を入力するだけ）File Provider で別途動的設定ファイルを記述する必要あり
学習コスト非常に低い（5 分で使い始められる）中程度（Router / Middleware / Service の概念理解が必要）
最適な用途内部 DNS 転送、小規模プロジェクト、コンテナと物理機の混在環境純粋な Docker / K8s 環境、動的なコンテナ群、完全自動デプロイ
