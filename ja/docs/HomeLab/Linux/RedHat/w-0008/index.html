Red Hat / Fedora DNF 実用コマンドとメンテナンスTipsメモ

1. はじめに：YUM から DNF へのモダンな移行​

Red Hat 系 OS のベテランユーザーなら yum の使用に非常に慣れていることでしょう。しかし、RHEL 8 / CentOS 8 以降、基盤となるパッケージ管理ツールは完全に dnf (Dandified YUM) へと置き換わっています。

dnf は、従来の yum で課題となっていたメモリ消費量の大きさや依存関係解決の遅さを解消しました。ターミナルで yum と入力しても動作はしますが（システムが dnf へのエイリアスを設定しているため）、今後は直接 dnf と入力するよう癖をつけることを強く推奨します。

(注：極小サイズのコンテナイメージや VMware Photon OS を使用している場合は、microdnf や tdnf を見かけることがあります。これらは dnf の軽量な C 言語実装版であり、コマンドの使い方は 95% 以上共通しています。)

2. 基本メンテナンス：システムのインストールと更新​

1. システム全体のアップデート リポジトリと照合し、インストール済みの全ソフトウェアを自動で更新します。

sudo dnf upgrade -y
# （註：在 dnf 中，update 跟 upgrade 基本上是同義詞，官方建議使用 upgrade）

2. パッケージの検索とインストール

# 安裝特定套件
sudo dnf install <套件名稱>

# 模糊搜尋套件
dnf search <關鍵字>

# 神奇指令：用「檔案路徑」來反查是哪個套件提供的 (Provides)
# 例如你缺了某個指令卻不知道要裝什麼套件，可以直接查：
dnf provides */ifconfig

3. パッケージのアンインストールと「孤立パッケージ」の削除 (Orphans)​

Red Hat 系ディストリビューションは、不要な孤立パッケージ（Orphans）を整理する仕組みがデフォルトの Debian よりも賢く設計されています。現在の DNF ではデフォルト設定（clean_requirements_on_remove=True）により、ソフトウェアを削除する際に不要になった依存パッケージも同時に削除してくれます。

1. パッケージの削除

sudo dnf remove <套件名稱>

2. 孤立パッケージの削除 (Orphans) DNF は削除処理がクリーンですが、リポジトリの変更などに伴い不要な依存パッケージが残ることがあります。念のため定期的にクリーンアップしておくと安心です。

sudo dnf autoremove

4. ディスク容量の解放：キャッシュの削除 (Cache)​

DNF はダウンロードしたメタデータ（Metadata）やインストール用ファイル（.rpm）をすべて /var/cache/dnf/ に保存します。これが VM のディスク容量を圧迫する最大の元凶になりがちです。

1. キャッシュの手動クリーンアップ

# 安全清理：只清除下載過的 rpm 安裝檔，保留 metadata
sudo dnf clean packages

# 深度清理：把安裝檔和 metadata 全部清空（釋放最大空間）
sudo dnf clean all

注意： clean all を実行すると、次回 dnf install や dnf search を実行した際に、数十 MB あるリポジトリの一覧（Metadata）を最初から再取得するため時間がかかります。

5. 救命ツール：履歴のロールバック (History) とバージョンロック (Versionlock)​

これは DNF が誇る最強のキラー機能です。古いファイルを自力で探してダウングレードする必要がある Arch や Debian と比べ、DNF には「タイムマシン」が標準搭載されています。

1. 強力な切り札：History を使ってアップデート前の状態に戻す システム更新後に環境が壊れてしまっても慌てる必要はありません。history を使って更新操作全体を「元に戻す（undo）」ことができます。

# 1. 查詢 DNF 執行紀錄（會列出一個清單，最左邊有 ID 編號）
dnf history

# 2. 檢視某次 ID 到底裝了/更新了什麼東西 (假設 ID 是 15)
dnf history info 15

# 3. 時光倒流！把 ID 15 做的所有變更「復原 (undo)」
sudo dnf history undo 15

2. 単一パッケージの直接ダウングレード 履歴操作を使わず、特定のパッケージだけを 1 つ前のバージョンに戻したい場合は次のようにします。

sudo dnf downgrade <套件名稱>

3. アップグレード防止のためのバージョンロック (Versionlock) 特定のソフトウェア（例：特定バージョンの Docker など）をダウングレードした後、次回のシステム更新で勝手にバージョンが上がらないようにするには、versionlock プラグインを導入します。

# 安裝 DNF 核心外掛套件
sudo dnf install dnf-plugins-core

# 將套件上鎖
sudo dnf versionlock add <套件名稱>

# 查詢目前被鎖定的套件有哪些
dnf versionlock list

# 解除鎖定
sudo dnf versionlock delete <套件名稱>
# 或是全解鎖
sudo dnf versionlock clear
Updated 2026-11-27

Fedora 41 以降（DNF5 へ移行済み）の環境では、プラグインパッケージ名が dnf5-plugins に変更されています（sudo dnf install dnf5-plugins でインストールしてください）。RHEL 8 / 9 / 10 および Rocky / AlmaLinux では引き続き dnf-plugins-core のままです。

6. 応用：サードパーティリポジトリと EPEL（エンタープライズ版必須）​

Red Hat / Rocky / AlmaLinux では、デフォルトの公式リポジトリが非常に保守的であるため、安定性を優先して便利なオープンソースソフトウェア（htop、新しめの nginx、certbot など）の多くが初期状態では含まれていません。

1. 必須リポジトリ：EPEL (Extra Packages for Enterprise Linux) これは Fedora コミュニティによって管理されている、エンタープライズ Linux 向けの高品質な追加パッケージリポジトリです。新しいマシンを立ち上げたら最初にインストールすべきリポジトリです。

sudo dnf install epel-release
sudo dnf upgrade

2. サードパーティリポジトリ (Repository) の追加 Red Hat 系のリポジトリ設定ファイルはすべて /etc/yum.repos.d/ 配下に配置され、拡張子は .repo になります。サードパーティのソース（Docker 公式リポジトリなど）を追加する際は、手動でファイルを作成するよりも組み込みの config-manager を使うのが最も迅速です。

# 新增一個 .repo
sudo dnf config-manager --add-repo https://download.docker.com/linux/centos/docker-ce.repo
Updated 2026-11-27

上記の --add-repo 構文は DNF4（RHEL 8 / 9 / 10、Rocky / AlmaLinux）向けです。Fedora 41 以降（DNF5）では、addrepo サブコマンドと --from-repofile= オプションに変更されています。 sudo dnf config-manager addrepo --from-repofile=https://download.docker.com/linux/fedora/docker-ce.repo

3. GPG 鍵の管理 DNF はデフォルトで鍵を自動処理します。新しいリポジトリから初めてソフトウェアをダウンロードする際、ターミナルにその鍵を信頼するか確認するプロンプトが表示されるので y を押すだけです。自動化デプロイスクリプトの場合は、事前に手動で鍵をインポートしておくこともできます。

sudo rpm --import https://download.docker.com/linux/centos/gpg

7. おまけ：コンテナホスト向けの超軽量バリアント TDNF (Tiny DNF)​

仮想化環境（ESXi など）でコンテナ最適化 OS である VMware Photon OS を稼働させている場合、OS 標準のパッケージマネージャーは tdnf (Tiny DNF) になります。

なぜ TDNF が必要なのか？ フル版の DNF は裏側で巨大な Python 環境とライブラリに強く依存しています。OS イメージを極限まで軽量化し、攻撃対象領域（アタックサーフェス）とリソース消費を削減するため、開発チームは Python への依存を完全に排除して C 言語で DNF を書き直しました。これが tdnf の由来です。

1. 違和感なく移行できる基本操作 互換実装であるため、DNF で身につけた操作感は tdnf でもほぼ 100% そのまま流用できます。

# 系統全面更新
sudo tdnf upgrade -y

# 安裝與移除套件
sudo tdnf install <套件名稱>
sudo tdnf remove <套件名稱>

# 搜尋套件
tdnf search <關鍵字>

# 清理快取（精簡空間必備）
sudo tdnf clean all

2. TDNF の制限事項と違い（ハマりポイント対策） コマンド構文はほぼ同じですが、「超軽量版」であるため巨大なプラグインエコシステムが省かれており、実運用上いくつか重要な違いに注意する必要があります。

  • History タイムマシンがない： tdnf にはオリジナルの DNF のように毎回インストール履歴を追跡する完全なローカルデータベースが内蔵されていないため、tdnf history undo のような高度なロールバック機能は使用できません。カーネルのアップグレードや大規模な更新を行う前には、万が一に備えて必ずハイパーバイザー側で VM スナップショット (Snapshot) を取得しておいてください。

  • リポジトリエコシステムが完全に独立している： Photon OS には独自の専用公式リポジトリがあります。CentOS / RHEL / Fedora 向けの EPEL (Extra Packages for Enterprise Linux) 設定ファイルを Photon OS に無理やり適用することは絶対に行わないでください。基盤となる glibc やカーネルバージョンの差異により、システムが即座に破損する可能性が極めて高いです。

  • Python 拡張プラグイン非対応： dnf-plugins-core やバージョン固定用の versionlock など、Python に依存する高度なプラグインは TDNF では使用できません。

3. リポジトリ設定とキャッシュ再構築 TDNF のリポジトリ設定ファイルは一般的な Red Hat 系と同様に /etc/yum.repos.d/ に格納されています。手動で .repo ファイルを追加・変更した場合や、ネットワーク異常で最新パッケージが取得できなくなった場合は、キャッシュを強制的に削除して再構築できます。

# 清除舊快取並強制從伺服器重新下載中繼資料
sudo tdnf clean all
sudo tdnf makecache
