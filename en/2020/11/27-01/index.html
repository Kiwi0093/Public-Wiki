Ladders and Their Accessories

November 27, 2020 · 9 min read
info

info

This article was reposted from the old site archive.

The day before yesterday, I picked up another cheap VPS from RackNerd's Thanksgiving sale—getting two years of usage for around 18 USD.

VLESS​

I mainly bought this one to test out VLESS configuration and usage, so as soon as I got it, I went straight to setting up VLESS. As usual, the detailed installation notes will go into the Wiki, so I won't specifically go into the installation and setup details here—let's just talk about my initial impressions.

Motivation​

Even though I know VLESS was created because VMess has issues that make it 100% detectable, the "ladders" (proxies) I currently have all use the WS+TLS architecture, so they aren't actually that risky (and if that's considered risky, wouldn't VLESS be just as risky?). So it wasn't strictly necessary to switch to VLESS. Still, after seeing some recommendations from Chinese users saying VLESS performs much better (since removing all the encryption and authentication from the original VMess should theoretically make it faster),

I couldn't resist... (a classic example of impulse buying).

Differences​

When using VMess+WS+TLS, to save myself the trouble, I basically always recommended using Caddy to handle the WS+TLS part. However, with VLESS, because TLS has to be wrapped inside V2Ray itself, you need to specify the path to the SSL key. That turns Caddy's convenient automatic SSL certificate handling into a bit of an issue (actually it shouldn't really be a problem—it's just that because it's automatic, you still have to track down where it stores its keys and verify it yourself). On top of that, Caddy v2's configuration file became more complex compared to v1, and I'm not as familiar with its configuration logic and documentation as I am with Nginx or Apache (at the end of the day, it still comes down to my own limitations...).

Testing Platform​

Because Caddy was no longer needed, thanks to my bizarre habit, I naturally wanted to reinstall the entire OS instead of just uninstalling packages (I guess to some extent this is a bad habit spoiled by VMs—whenever I'm too lazy to make big changes, I just reinstall). So at first I started working on the Arch Linux machine at home that runs my backup V2Ray. Since I was also rewriting my Arch Linux automated install script recently, I got carried away and started debugging the script while reinstalling the system at the same time (speaking of which, I have to say it's really annoying that the installation process changed slightly again, forcing me to rewrite core parts of the script...). So the day before yesterday, most of my time was spent tweaking the script and reinstalling the OS...

Later, when I got the RackNerd VPS, I took the opportunity to deploy directly on it. These VPS providers basically only offer Debian/Ubuntu or CentOS-based distros, and none of the Arch Linux I like to use...

After looking at some tutorials online, I felt using Arch Linux might actually be simpler—at the very least, pacman can handle the installation without needing to run an external script, and you don't need to edit crontab for auto-updates (speaking of which, auto-updates on my other VPSes basically all broke because the install script path changed).

Server-Side Thoughts​

Because V2Ray can handle the WS+TLS part by itself, I initially thought naively that I wouldn't need to install Nginx or Apache during setup. However, thinking about it afterward, it's still easier to handle SSL keys with Certbot if a web server is installed, so I installed one anyway...

Overall, though, the fact that once V2Ray is configured you can run WebSocket without even starting Nginx/Apache is pretty convenient—it saves you from configuring an extra web server. That said, in the end you probably still need to set up the web server anyway, otherwise its fallback won't work properly.

You can see this trend aligns with the V2Ray team's vision: from the beginning, V2Ray never intended to be just a SOCKS server. What they want is more like a comprehensive, extensible network management Swiss Army knife—with DNS, routing tables, communication protocols, encryption, and so on. If one day it includes a full web server module rather than just WS functionality, I probably wouldn't be surprised at all.

Right now it's set up with VLESS+WS+TLS in the most minimal way following a template. Once the XTLS licensing issue is sorted out later, I might also try VLESS+XTLS to see if it's really as powerful as people say (everyone says it's as fast as running unencrypted...).

Client-Side Thoughts​

Gateway V2ray client​

Yep, I switched my room's Gateway over to the VPS running VLESS+WS+TLS. It seems to work pretty normally. As for speed, it's probably bottlenecked by China Unicom's terrible network, so I can't tell at all whether it got faster... (so basically, my original goal wasn't achieved at all—well, comparing speed and efficiency without a decent network route is kind of a joke anyway, right??)

Right now I'm basically doing stability testing to see if there are any surprises over the next few days (hopefully pleasant ones, not scary ones).

Linux Client - QV2Ray+V2ray​

Because my Linux Desktop (the one I'm writing this blog post on right now) runs Manjaro, installing V2Ray is super easy, which makes me very grateful to the Arch team.

As for how it feels to use... well, I can only say I only tried it for a short moment before stopping, mainly because there's currently no WiFi at the office to connect to (so this post probably won't be published on time on the day I wrote it).

However, it seemed to perform about the same as the Gateway—no noticeable difference, probably still bottlenecked by the network route.

Android Client - V2RayNG​

Since there aren't many clients that support VLESS yet, I had no choice but to newly install V2RayNG on my phone. I have to say, it feels more stable and nicer to use than BifrostV—honestly, this app is the main reason I wanted to write this post (wait, so everything before this was just filler?!).

Pros (Very Subjective)​

  • QR code / barcode compatible with QV2Ray

    First, this app supports the same barcode format as Qv2ray, which follows the "standard specification." Compared to BifrostV, which uses its own proprietary format, this is much more convenient to use. That said, it's not that BifrostV was being stubborn, rather that there wasn't a clearly defined V2Ray link barcode standard earlier—but either way, being able to use the same barcode format is definitely much nicer.

  • No ads, and a GUI to my taste

    Although I'm not completely opposed to free apps having ads, having a clean app without unnecessary ads really makes you feel happy.

    Maybe it's because the Shadowsocks app left such a good impression on me earlier—its clean GUI style, responsiveness, and being the first app that let me reliably climb over the wall—that I have a really high affinity for V2RayNG's interface, which looks a lot like shadowsocks.

  • Fast response and high stability

    When I first switched to BifrostV for V2Ray, I often felt its responsiveness and stability weren't as good as shadowsocks—it would frequently hang upon opening, or randomly disconnect mid-session, and things like that. At the time, though, I felt there wasn't any other alternative that covered so many protocols, so I just put up with it—until I switched to V2RayNG for VLESS, and everything changed...

    It brought back that feeling of using shadowsocks again. Though honestly, since I rarely wander around outside, I don't actually rely on proxy apps on my phone or tablet all that heavily—and once I'm back in my room, the WiFi is already behind a Gateway that handles the proxy, so I basically don't need to proxy again on the device...

Cons​

  • DNS issues

    I'm not sure whether it's a VLESS issue or a V2RayNG issue, but it doesn't handle DNS poisoning very well. With the exact same settings, connecting to VMess+WS+TLS works completely fine, but as soon as I connect to VLESS+WS+TLS, DNS errors occur and I can't connect. After randomly trying things out, only the following settings worked properly:

    • Domain Strategy - Either IPIfNonMatch or IPOnDemand works
    • Predefined Rules - Bypass LAN and Mainland China
    • Enable Local DNS - Must NOT be enabled
    • Remote DNS - Change to Google's 8.8.8.8

    That's how it is for now, though logically there shouldn't be an issue. Maybe once I figure out what's causing it later, I'll come back and update this.

Conclusion​

In short, proxy-related tech is probably something that only people living in the Great Power the Celestial Empire ever bother learning. Just like my master said, "That's a very niche skill tree—among this group, probably only you who's stationed over there would put points into it." So I could only dig through online resources, pick up a little superficial knowledge, and embarrass myself by sharing it here.

Fortunately, there are still plenty of resourceful folks in the Celestial Empire, so related info is still easy to find—well, yes... it's easy to find once you've scaled the wall and can use Google, whereas inside the wall you can't find a single article...

So when it comes down to it, a "ladder" is really just something where you need a tool to get over the wall the first time. Once you have that, building any other ladder afterward is relatively easy...

That said, building ladders is inherently a small act of defiance against the Celestial Empire's state apparatus—it requires constant updates and refinement. If you truly want a permanent solution once and for all,

physically getting yourself out ("emigrating in person") is still the most practical option.
