Debian / Ubuntu APT Package Management and System Maintenance Notes

I. Introduction: Modern Package Management with Nala (Recommended)​

In the Debian family, the underlying package management tool is dpkg, while the high-level command we use daily is apt (which replaced the older apt-get).

Recommended Tool: Nala

If you are accustomed to the clean and intuitive interface of Arch's yay, it is strongly recommended to install nala on Debian / Ubuntu. It is a frontend wrapper for apt featuring clearer formatting, parallel download acceleration, and history rollback capabilities.

# Install Nala
sudo apt update
sudo apt install nala

Once installed, you can seamlessly replace almost all your daily apt commands with nala (e.g., sudo nala update). The basic commands below will still focus on native apt, but the underlying logic applies to both.

II. Basic Maintenance: Installation and System Updates​

1. Comprehensive System Update

Updates in the Debian family involve two steps: refreshing the local package list and then performing the actual upgrade:

sudo apt update && sudo apt upgrade -y

Advanced Knowledge: Difference between apt upgrade and apt full-upgrade?

  • upgrade (Safe Upgrade): Upgrades existing packages only. If a new version of a package requires "removing" other existing packages to be installed, upgrade chooses to skip that package, keeping the current state for stability.
  • full-upgrade (Full Upgrade): Allows the system to actively remove blocking obsolete dependencies during upgrades. Typically used when performing major distribution upgrades (e.g., Ubuntu 22.04 to 24.04) or when package dependencies are deadlocked. (Note: In legacy commands, the equivalent is apt-get dist-upgrade)

2. Searching and Installing Packages

# Install a specific package
sudo apt install <package_name>

# Search for packages (supports regular expressions)
apt search <keyword>

III. Package Uninstallation and "Orphan" Cleanup​

The most common mistake when uninstalling packages in Debian systems is using remove alone, leaving configuration files and dependencies behind.

1. Clean Removal of Main Applications

  • Standard Removal: Deletes the program binary only while retaining configuration files you modified under /etc.

    sudo apt remove <package_name>

  • Complete Removal (Purge): Removes the program along with all global configuration files (excluding settings inside your personal home directory ~/.config/).

    sudo apt purge <package_name>

2. Cleaning Up Orphaned Packages

Dependencies installed automatically to satisfy a software package often remain even after the main application is uninstalled. Debian provides built-in commands to clean these up:

# Remove all orphaned packages that are no longer needed
sudo apt autoremove

# Advanced: Clean up orphaned packages along with their configuration files (Recommended)
sudo apt --purge autoremove

IV. Freeing Up Disk Space: Cache Cleanup​

Every .deb installer downloaded via apt install is cached in /var/cache/apt/archives/. On long-running VMs or machines with limited disk space, this consumes significant storage.

1. Manual Cache Cleanup

# Safe cleanup: Delete only outdated installer versions that can no longer be downloaded from repositories
sudo apt autoclean

# Deep cleanup: Completely empty the cache folder to free up maximum space
sudo apt clean

Automation Tip: Debian / Ubuntu actually has built-in scheduled tasks. As long as unattended-upgrades is installed, the system silently cleans up outdated caches in the background by default, eliminating the need to manually write Systemd Timers like on Arch.

V. Lifesaving Tools: Package Downgrade and Hold​

Although the Debian family is relatively stable, adding third-party PPAs or external repositories can still occasionally introduce broken updates.

1. Finding Historical Versions

First, check which older versions are available on the repository servers.

apt-cache madison <package_name>
# or
apt list -a <package_name>

This prints all available version numbers for the package (e.g., 1.2.3-1ubuntu2).

2. Performing a Downgrade Installation

Once you find the desired version number, force installation by appending = directly (this overwrites the buggy newer version):

sudo apt install <package_name>=<version_number>

3. ⚠️ Critical Step: Version Hold to Prevent Upgrades

After downgrading, you must "hold" the package to prevent accidentally upgrading it the next time you run apt upgrade:

sudo apt-mark hold <package_name>

Packages on hold are automatically ignored by apt even when newer versions are released.

4. How to Release a Downgrade Hold (Unhold)

When an official bug fix is released and you decide to give it another try, simply release the hold:

sudo apt-mark unhold <package_name>

Once unheld, the next apt upgrade will upgrade the package normally.

VI. Advanced: Adding Third-Party Repositories and GPG Keys Correctly (Saying Goodbye to apt-key)​

Previously, when adding third-party software repositories (such as Docker, Node.js, Grafana), we commonly used sudo apt-key add to add GPG keys. Doing so today triggers a prominent apt-key is deprecated warning.

Why was it deprecated? Because apt-key places keys into the system's global trusted keyring (/etc/apt/trusted.gpg). This means if you add a key for a minor utility, that key gains permission to forge and verify system-core level packages—a massive security vulnerability.

Modern Standard Practice (Signed-by Binding): The modern specification dictates storing keys independently in dedicated directories and strictly specifying in repository configuration files that "this repository may only be verified using this specific key."

Below is the standard workflow compliant with Ubuntu 22.04+ and Debian 12+ (taking a fictional example repository as an example):

1. Create a Dedicated Directory for Keys The system now recommends storing third-party keys centrally under /etc/apt/keyrings/ (create the folder if older systems lack it):

sudo mkdir -p /etc/apt/keyrings

2. Download and Convert the Key (Dearmor) Most third-party keys are provided as ASCII text files (.asc or .pub), but apt now prefers binary .gpg files. Download via curl and convert using gpg --dearmor into the newly created directory:

curl -fsSL https://example.com/key.pub | sudo gpg --dearmor -o /etc/apt/keyrings/example.gpg

3. Add Repository Source and Bind the Key Create a list file for the software under /etc/apt/sources.list.d/, making sure to append [signed-by=...] right after deb:

echo "deb [arch=amd64 signed-by=/etc/apt/keyrings/example.gpg] https://example.com/apt stable main" | sudo tee /etc/apt/sources.list.d/example.list

Explanation: With signed-by=/etc/apt/keyrings/example.gpg specified, the system verifies software downloaded from example.com using strictly this dedicated key, preventing unauthorized interference with other system packages.

4. Update Cache Files Finally, update the package list to eliminate deprecation warnings:

sudo apt update
Updated 2026-11-27

In newer Ubuntu 24.04+ and Debian 12 / 13+ environments, consider the following modern details:

  1. Directory & Key Permissions: When creating the directory, use sudo mkdir -p -m 0755 /etc/apt/keyrings, and ensure the converted .gpg file is readable (sudo chmod a+r /etc/apt/keyrings/example.gpg) to prevent the low-privilege _apt user from failing to read the key during apt update.
  2. Dynamic Architecture Detection: Hardcoding arch=amd64 on ARM64 hosts (such as Raspberry Pi) causes fetch failures; substitute it with arch=$(dpkg --print-architecture).
  3. DEB822 .sources Format: Modern systems are phasing out traditional single-line .list files in favor of structured /etc/apt/sources.list.d/example.sources (using the Signed-By: field); APT 3.0+ (Debian 13 / Ubuntu 24.10+) also provides sudo apt modernize-sources to automatically convert legacy .list files to .sources format.
