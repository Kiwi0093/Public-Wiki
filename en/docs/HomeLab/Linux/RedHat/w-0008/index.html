Red Hat / Fedora DNF Practical Commands & Maintenance Tips Notes

info

This article was automatically translated by Google "Gemini". The author does not guarantee its accuracy or wording.

I. Introduction: The Modern Transition from YUM to DNF​

In the Red Hat family, veteran users are likely very accustomed to using yum. However, starting from RHEL 8 / CentOS 8, the underlying package management tool has been completely replaced by dnf (Dandified YUM).

dnf solved the issues of excessive memory usage and slow dependency resolution that plagued yum in the past. Although typing yum in the terminal still works (due to a system alias pointing to dnf), it is strongly recommended to build the muscle memory of typing dnf directly.

(Note: If you are using a minimalist container image or VMware Photon OS, you might see microdnf or tdnf, which are lightweight C-language implementations of dnf with over 95% commonality in command usage.)

II. Basic Maintenance: Installing and Updating Systems​

1. Comprehensive System Upgrade This automatically compares repositories and updates all installed software:

sudo dnf upgrade -y
# (Note: In dnf, update and upgrade are basically synonyms; official recommendation is to use upgrade)

2. Searching and Installing Packages

# Install a specific package
sudo dnf install <package_name>

# Fuzzy search for packages
dnf search <keyword>

# Magic command: Use a "file path" to reverse-lookup which package provides it (Provides)
# For example, if you miss a command and don't know what package to install, you can directly query:
dnf provides */ifconfig

III. Package Uninstallation and Clearing "Orphans"​

The Red Hat family's mechanism for cleaning up orphaned packages is much smarter than Debian's default. Modern DNF defaults (clean_requirements_on_remove=True) automatically sweep away unneeded dependency packages when removing software.

1. Remove a Package

sudo dnf remove <package_name>

2. Clear Orphaned Packages (Orphans) Although DNF removes things cleanly, repository changes can sometimes leave behind unwanted dependencies. Regularly clearing them keeps things tidy:

sudo dnf autoremove

IV. Freeing Disk Space: Cache Cleaning​

Every time DNF downloads metadata and installation files (.rpm), it stores them in /var/cache/dnf/. This is often the primary culprit behind consumed VM disk space.

1. Manual Cache Cleanup

# Safe cleanup: Only clear downloaded rpm installation files, keeping metadata
sudo dnf clean packages

# Deep cleanup: Clear both installation files and metadata entirely (frees maximum space)
sudo dnf clean all

Note: After running clean all, the next time you run dnf install or dnf search, the system will take longer to re-download several tens of megabytes of lists (Metadata).

V. Lifesaving Tools: History Rollback (History) and Package Locking (Versionlock)​

This is DNF's most powerful killer feature! Compared to Arch or Debian, which require manually hunting down old files for downgrading, DNF has a built-in "time machine."

1. Super Skill: Using History to Roll Back to Pre-Update State If your system breaks after an update, don't panic—use history to "undo" the entire update action:

# 1. Query DNF execution history (lists a log with an ID number on the far left)
dnf history

# 2. Inspect what a specific ID installed/updated (assuming ID is 15)
dnf history info 15

# 3. Time travel! "Undo" all changes made by ID 15
sudo dnf history undo 15

2. Direct Downgrade of a Single Package If you don't want to use history and simply want to revert a specific package to the previous version:

sudo dnf downgrade <package_name>

3. Package Anti-Upgrade Locking (Versionlock) When you have downgraded a piece of software (e.g., a specific version of Docker) and do not want it to be upgraded during the next update, you need to install the versionlock plugin:

# Install DNF core plugin package
sudo dnf install dnf-plugins-core

# Lock a package
sudo dnf versionlock add <package_name>

# Query currently locked packages
dnf versionlock list

# Unlock
sudo dnf versionlock delete <package_name>
# Or unlock all
sudo dnf versionlock clear
Updated 2026-11-27

In Fedora 41+ (which has switched to DNF5), the plugin package name has changed to dnf5-plugins (install using sudo dnf install dnf5-plugins instead); RHEL 8 / 9 / 10 and Rocky / AlmaLinux retain dnf-plugins-core.

VI. Advanced: Third-Party Repositories and EPEL (Essential for Enterprise)​

In Red Hat / Rocky / AlmaLinux, default official repositories are very conservative for the sake of stability, meaning many useful open-source software packages (such as htop, newer versions of nginx, certbot) are not available by default.

1. Essential Repository: EPEL (Extra Packages for Enterprise Linux) Maintained by the Fedora community, this is a high-quality extra repository specifically for Enterprise Linux. Installing it is the first thing to do on a new machine:

sudo dnf install epel-release
sudo dnf upgrade

2. Adding Third-Party Repositories Red Hat family repository configuration files are located under /etc/yum.repos.d/ with the extension .repo. To add a third-party source (such as Docker's official source), you don't need to create files manually; using the built-in config-manager is fastest:

# Add a .repo file
sudo dnf config-manager --add-repo https://download.docker.com/linux/centos/docker-ce.repo
Updated 2026-11-27

The --add-repo syntax above applies to DNF4 (RHEL 8 / 9 / 10, Rocky / AlmaLinux). In Fedora 41+ (DNF5), it has changed to the addrepo subcommand and --from-repofile= parameter: sudo dnf config-manager addrepo --from-repofile=https://download.docker.com/linux/fedora/docker-ce.repo

3. GPG Key Management DNF handles keys automatically by default. When you first download software from a new repo, the terminal prompts you whether to accept the key—pressing y suffices. For automated deployment scripts, keys can be imported manually ahead of time:

sudo rpm --import https://download.docker.com/linux/centos/gpg

VII. Ultimate Bonus: Minimalist Variant TDNF (Tiny DNF) Built for Container Hosts​

If you are running VMware Photon OS, which is optimized specifically for containers in a virtualization environment (such as ESXi), the built-in package manager will be tdnf (Tiny DNF).

Why TDNF? Full DNF heavily depends on a bulky Python environment and libraries. To keep the operating system image extremely lean, reduce the attack surface, and minimize resource consumption, the development team rewrote DNF in C, completely stripping out Python dependencies—hence the origin of tdnf.

1. Seamlessly Transferable Basic Operations Because it is a compatible implementation, the muscle memory built from DNF can be applied almost 100% to tdnf:

# Comprehensive system update
sudo tdnf upgrade -y

# Install and remove packages
sudo tdnf install <package_name>
sudo tdnf remove <package_name>

# Search packages
tdnf search <keyword>

# Clean cache (essential for saving space)
sudo tdnf clean all

2. Limitations and Differences of TDNF (Pitfall Guide) Although command syntax is nearly identical, because it is a "minimalist version" lacking the massive plugin ecosystem, there are several key differences to note in practice:

  • No History Time Machine: tdnf lacks a built-in local database as robust as original DNF to track every installation history, so advanced rollback functions like tdnf history undo are unavailable. Before performing core upgrades or major updates, be sure to take a VM snapshot at the Hypervisor level just in case.

  • Completely Independent Repository Ecosystem: Photon OS has its own dedicated official software repository. Never attempt to force CentOS / RHEL / Fedora EPEL (Extra Packages for Enterprise Linux) configuration files onto Photon OS; differences in underlying glibc and kernel versions are highly likely to crash the system directly.

  • No Python Extension Support: High-level Python-dependent plugins such as dnf-plugins-core or version-locking versionlock cannot be used on TDNF.

3. Repository Configuration and Cache Reconstruction TDNF repository configuration files are identical to standard Red Hat families, stored under /etc/yum.repos.d/. If you manually added or modified a .repo file, or if network connectivity issues prevent fetching the latest software, you can forcibly clear and rebuild the cache:

# Clear old cache and force re-download metadata from the server
sudo tdnf clean all
sudo tdnf makecache
