Gitea Lightweight Self-Hosted Git Server Setup and Maintenance Manual (Wiki)

1. Architectural Positioning and Core Design Principles​

When focusing on HomeLab internal automation (such as Ansible, Docusaurus, and Docker Compose repositories), the architecture has the following key design highlights:

  • Pure Intranet HTTP Strategy:

    In an isolated intranet, the Git server is only used by internal VMs or physical nodes to pull code (e.g., ansible-pull -U http://git.internal.local/admin/homelab.git). Using internal HTTP completely eliminates the management hassle of intranet self-signed CA certificate expiration or manually installing a trusted root CA on each client node.

  • Database Selection: Why Abandon SQLite for MySQL / MariaDB?

    • SQLite is inherently a single-file database and triggers database-level locks during high-frequency concurrent writes.
    • When multiple nodes run ansible-pull simultaneously, or when multiple Git hooks/CI runners report status concurrently, it easily triggers fatal database is locked (5) errors, causing Git push/pull operations to fail and abort.
    • Adopting standalone MySQL / MariaDB completely eliminates locking timeout issues through row-level locks and connection pooling.

  • SSH Port Conflict Avoidance:

    If you want to allow Git over the SSH protocol (git@host:repo.git) inside a container, port 22 inside the container must not be directly mapped to port 22 on the host (to avoid conflicts with the host's own SSH management port). It typically needs to be mapped as 2222:22, or pass-through can be achieved via the host OpenSSH AuthorizedKeysCommand. Alternatively, using Macvlan to assign an independent IP and pointing the SSH domain to that IP avoids port mapping altogether, though HTTP and SSH will connect through different domains.

2. Docker Compose Complete Deployment Template​

Step 1: Create Dedicated Directories and Permissions​

sudo mkdir -p /opt/gitea/data /opt/gitea/config /opt/gitea/mysql
# The official Gitea image runs as UID 1000 by default
sudo chown -R 1000:1000 /opt/gitea/data /opt/gitea/config

Step 2: docker-compose.yml Configuration​

Configure /opt/gitea/docker-compose.yml as follows:

services:
  server:
    image: gitea/gitea:latest
    container_name: gitea
    restart: unless-stopped
    depends_on:
      db:
        condition: service_healthy
    environment:
      - USER_UID=1000
      - USER_GID=1000
      - TZ=Asia/Taipei
      # Crucial: External access URL (affects the generation path of Git clone links copied in the frontend UI)
      - GITEA__server__ROOT_URL=http://git.internal.local/
      - GITEA__server__HTTP_PORT=3000
      - GITEA__server__DOMAIN=git.internal.local
      - GITEA__server__SSH_PORT=2222
      - GITEA__server__SSH_LISTEN_PORT=22
      # Database connection configuration (supports GITEA__*__* format to auto-override app.ini)
      - GITEA__database__DB_TYPE=mysql
      - GITEA__database__HOST=db:3306
      - GITEA__database__NAME=gitea
      - GITEA__database__USER=gitea
      - GITEA__database__PASSWD=gitea_secret_password
    volumes:
      - /opt/gitea/data:/data
      - /opt/gitea/config:/etc/gitea
      - /etc/timezone:/etc/timezone:ro
      - /etc/localtime:/etc/localtime:ro
    ports:
      # Git SSH service port (external access uses 2222)
      - "2222:22"
      # If going directly through NPM reverse proxy on the same Docker network, port 3000 doesn't even need external mapping
      - "3000:3000"
    networks:
      - backend

  db:
    image: mariadb:10.11
    container_name: gitea_db
    restart: unless-stopped
    command:
      - "mariadbd"
      - "--character-set-server=utf8mb4"
      - "--collation-server=utf8mb4_unicode_ci"
      - "--innodb-file-per-table=1"
    environment:
      - TZ=Asia/Taipei
      - MARIADB_ROOT_PASSWORD=db_root_secret_password
      - MARIADB_DATABASE=gitea
      - MARIADB_USER=gitea
      - MARIADB_PASSWORD=gitea_secret_password
    volumes:
      - /opt/gitea/mysql:/var/lib/mysql
    networks:
      - backend
    healthcheck:
      test: ["CMD", "healthcheck.sh", "--connect", "--innodb_initialized"]
      interval: 5s
      timeout: 5s
      retries: 10

networks:
  backend:
    driver: bridge
    # If using a shared npm-network, you can mount an external network directly:
    # external: true
    # name: npm-network

Improvement Notes:

  1. Previously, mysql:latest occasionally encountered connection interruptions caused by default authentication plugin updates (such as caching_sha2_password). Here, long-term supported mariadb:10.11 is recommended for lower resource overhead and better compatibility.
  2. Added healthcheck and depends_on: condition: service_healthy to ensure Gitea starts only after the database has fully completed initialization, eliminating DB Connection Refused errors during startup.

3. Reverse Proxy Integration (Nginx Proxy Manager)​

When connecting NPM and Gitea on the same custom network (such as backend or an external shared npm-network), the reverse proxy configuration is extremely clean:

NPM Proxy Host Configuration​

  1. Go to Hosts -> Proxy Hosts -> Add Proxy Host.

  2. Details tab settings:

    • Domain Names: git.internal.local
    • Scheme: http
    • Forward Hostname / IP: gitea (enter the container name directly)
    • Forward Port: 3000 (Gitea container default listening port)
    • Check Websockets Support (required for Gitea internal notifications).

  3. Large File Upload Interruption Prevention (Important):

    • Go to the Advanced tab and paste the following into the custom Nginx configuration block:
    # Allow large Git pushes (default is only 1MB; large projects or binary files will be blocked)
    client_max_body_size 512M;

4. Practical Tips with Ansible-Pull​

When using ansible-pull for self-configuration of nodes in a HomeLab, the advantages of Gitea's pure HTTP are particularly prominent:

4.1 Create a Passwordless Read-Only Account or Access Token​

  1. Create an account dedicated to automated maintenance in Gitea (e.g., ci-bot).
  2. Under Settings -> Applications for that account, create a Personal Access Token with read:repository permissions.

4.2 Execute ansible-pull on the Node Side​

Run automated synchronization on the client host (no SSH keys or trusted certificates required):

# Perform pure HTTP pull and execution using the token
ansible-pull -U http://ci-bot:<YOUR_TOKEN>@git.internal.local/infra/homelab-ansible.git \
  -i localhost, \
  local.yml

5. Common Troubleshooting and Tuning​

Anomaly SymptomRoot CauseTroubleshooting Steps
Git Push error: RPC failed; HTTP 413 curl 22 The requested URL returned error: 413Triggered Nginx's default client_max_body_size limit when passing through NPMAdd client_max_body_size 512M; (or higher) to NPM's advanced settings, and verify [repository.upload] FILE_MAX_SIZE = 512 in Gitea's app.ini.
URL copied from Web UI Clone button turns into http://localhost:3000/...ROOT_URL is not resolved correctlyCheck if the environment variable GITEA__server__ROOT_URL=http://git.internal.local/ is set (make sure it ends with a slash /), and restart the container.
SSH Clone fails (Permission denied / Connection refused)External port mapping confusion or mixed up host vs container SSH1. Ensure port 2222 is specified during connection: git clone ssh://git@git.internal.local:2222/user/repo.git.
2. To avoid typing 2222, define an alias in the client's ~/.ssh/config.
Forgot Administrator PasswordUnable to log in via Web UI to resetUse the container internal CLI to reset the admin password in one click:
docker compose exec --user 1000 server gitea admin user change-password --username admin --password "New_Password"

6. Data Backup and Disaster Recovery​

Gitea provides a dedicated backup command that fully packages database SQL, bare repositories, user settings, and plugin data into a single ZIP archive:

# 1. Execute one-click backup command inside the container
docker compose exec -T --user 1000 server gitea dump -c /data/gitea/conf/app.ini --file /data/gitea-dump.zip

# 2. Move the backup file from the host directory to the backup storage area
sudo mv /opt/gitea/data/gitea-dump.zip /opt/backups/gitea-$(date +%F).zip

# Restoration method (in a brand new clean directory):
# unzip gitea-dump.zip
# Import the restored SQL into MariaDB, and overwrite the data directory back to /opt/gitea/data/gitea
note

When executing gitea dump, please confirm whether the app.ini path specified by -c is /etc/gitea/app.ini or /data/gitea/conf/app.ini based on your container mount and environment variable settings.
