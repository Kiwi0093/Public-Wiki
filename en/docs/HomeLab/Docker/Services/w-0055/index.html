WireGuard VPN Server (Docker) and Cross-Platform Client Setup

1. Core Mechanics and Network Architecture​

WireGuard adopts a peer-to-peer (P2P) concept. Every machine in the architecture is essentially a "Peer," though the host with a fixed public IP address is typically treated as the "Server / Relay Node":

[Client (Phone / Laptop)] (WireGuard IP: 10.13.13.2)
        │
        │ UDP (Encrypted packets, default port 51820)
        ▼
[WireGuard Server Container] (WireGuard IP: 10.13.13.1 / Host Public IP:Port)
        │
        ├─► [LAN Devices (LAN Access)] (192.168.1.0/24)
        └─► [Internet (Full Tunnel Forwarding)] (0.0.0.0/0)

  • UDP Protocol: WireGuard runs entirely on UDP. When no data is being transmitted, it sends zero probe packets, behaving essentially like "silence with no response" and offering excellent scan-resistance.

  • Cryptokey Routing: The server strongly binds each client's Public Key to its assigned internal IP. Only packets with a valid signature and a source IP matching the declared IP are accepted.

2. Docker Compose Server Deployment (LinuxServer.io)​

The standout feature of LinuxServer.io's image is that upon startup, based on the PEERS names declared in environment variables, it automatically generates the corresponding client configuration files (peer_*.conf) and terminal QR codes, saving you from the tedious process of manually generating keys and setting up routes.

Step 1: Create Dedicated Directory​

sudo mkdir -p /opt/wireguard/config

Step 2: Complete docker-compose.yml Configuration​

Define in /opt/wireguard/docker-compose.yml:

services:
  wireguard:
    image: ghcr.io/linuxserver/wireguard:latest
    container_name: wireguard
    restart: unless-stopped
    cap_add:
      - NET_ADMIN
      - SYS_MODULE
    environment:
      - PUID=1000
      - PGID=1000
      - TZ=Asia/Taipei
      # 1. External access address (Public static IP or DDNS domain name)
      - SERVERURL=vpn.example.com
      # 2. External listening UDP port
      - SERVERPORT=51820
      # 3. Client naming list (comma-separated, automatically generates corresponding configuration files)
      - PEERS=phone,laptop,ipad
      # 4. DNS servers assigned to clients (can be 1.1.1.1, 8.8.8.8, or internal AdGuard Home IP)
      - PEERDNS=1.1.1.1
      # 5. WireGuard internal virtual subnet (Server automatically acquires .1 in this subnet)
      - INTERNAL_SUBNET=10.13.13.0/24
      # 6. Default AllowedIPs range pushed to clients (0.0.0.0/0 means full traffic forwarding)
      - ALLOWEDIPS=0.0.0.0/0
    volumes:
      - /opt/wireguard/config:/config
      - /lib/modules:/lib/modules:ro
    ports:
      - "51820:51820/udp"
    sysctls:
      - net.ipv4.conf.all.src_valid_mark=1

Core Parameters & Permissions Note:

  • cap_add: [NET_ADMIN, SYS_MODULE]: The container needs to manipulate the host's virtual network interface (TUN) and load the WireGuard kernel module.

  • /lib/modules:/lib/modules:ro: Allows the container to load the host's WireGuard kernel driver for ultimate performance (natively built into Linux 5.6+ kernels).

  • net.ipv4.conf.all.src_valid_mark=1: Prevents packets from being dropped by rp_filter in multi-routing-table environments.

Start the service:

docker compose up -d

3. Retrieving Client Configurations and Connection Methods​

3.1 Mobile Devices (Android / iOS)​

  1. Install the official WireGuard app from Google Play or App Store.

  2. View the QR code generated by the container:

    # View logs to find the QR code for a specific peer
    docker compose logs -f wireguard
    # Or use the container's internal tool to display a specific peer (e.g., phone)
    docker compose exec wireguard /app/show-peer phone

  3. Open the mobile WireGuard app, tap the + button -> select "Scan from QR code" to instantly import and enable it.

3.2 Desktop & Linux Client Configuration Extraction​

All generated configuration files are saved in the host's mounted directory:

# View generated configuration files
ls -l /opt/wireguard/config/peer_laptop/
# Contents include:
# - peer_laptop.conf (Standard configuration file)
# - peer_laptop.png  (QR code image file)
# - privatekey-peer_laptop / publickey-peer_laptop

4. Linux Client Setup Practice (Taking Arch / Manjaro / Debian / Ubuntu as Examples)​

On Linux desktops or servers, there are two main connection methods: the traditional wg-quick CLI tool, and NetworkManager integrated with desktop network management.

Method A: Using wg-quick CLI (Recommended for Servers or Lightweight Environments)​

  1. Install utility packages:

    # Arch / Manjaro
    sudo pacman -S wireguard-tools

    # Ubuntu / Debian
    sudo apt-get install -y wireguard-tools

  2. Deploy configuration file:

    Copy the server-generated peer_laptop.conf to the client's /etc/wireguard/ and rename it to your preferred interface name (e.g., wg0.conf):

    sudo mkdir -p /etc/wireguard
    sudo cp peer_laptop.conf /etc/wireguard/wg0.conf
    # Strictly limit key file permissions (otherwise wg-quick will warn)
    sudo chmod 600 /etc/wireguard/wg0.conf

  3. Start and stop connections:

    # Start connection (interface name corresponds to filename wg0)
    sudo wg-quick up wg0

    # View connection status and transfer volume (Transfer RX/TX)
    sudo wg show

    # Disconnect
    sudo wg-quick down wg0

  4. (Optional) Set up automatic connection on boot:

    sudo systemctl enable wg-quick@wg0

Method B: Importing into NetworkManager / GUI (Recommended for Desktop Environments)​

If you use desktop systems like GNOME / KDE, you can import with a single nmcli command and then use the network icon in the top right corner of the system to toggle it:

# Import config file to create connection profile with a single command
sudo nmcli connection import type wireguard file /etc/wireguard/wg0.conf

# Enable connection
nmcli connection up wg0

# Disconnect
nmcli connection down wg0

(After importing, you can freely toggle switches and modify settings in the system's "Network Settings" graphical interface).

5. Core Pitfall: AllowedIPs Routing Planning (Full Tunnel vs. Split Tunnel)​

AllowedIPs in the client configuration file is the most common cause of "original network breaking as soon as VPN turns on" or "other server services becoming unreachable." It has dual functions:

  1. Local Route Injection: Determines which destination IP traffic from the local machine should be pushed into the WireGuard tunnel.

  2. Inbound Packet Filtering: Determines which source IP packets are allowed to be received by the WireGuard interface.

Scenario 1: Full Tunnel (Full Traffic Forwarding)​

When connecting to public Wi-Fi away from home, you want all network traffic to proxy out via your home / VPS WireGuard server:

[Peer]
# Includes all IPv4 and IPv6 subnets
AllowedIPs = 0.0.0.0/0, ::/0

Note:

When set to 0.0.0.0/0, WireGuard takes over the Default Gateway. If there are other services or local servers on the client's local subnet, you may need to ensure local LAN routes are excluded.

Scenario 2: Split Tunnel (Access Internal Network Devices Only)​

You only want to securely access remote home / datacenter internal devices (such as connecting back to a NAS, HomeLab, or viewing internal web pages), while regular web browsing (YouTube, Google) still goes through your original broadband:

[Peer]
# Route only remote internal subnets (e.g., 192.168.1.0/24) and WireGuard's own subnet (10.13.13.0/24) through VPN
AllowedIPs = 10.13.13.0/24, 192.168.1.0/24

6. NAT Traversal Keepalive: PersistentKeepalive​

WireGuard is stateless by default. If your client is behind NAT (home router, mobile hotspot 4G/5G), the router's NAT mapping table typically clears expired UDP connection states after tens of seconds to a few minutes. This causes "the client can send requests to the server, but when the server proactively sends data, it cannot reach the client" (e.g., delayed push notifications on the client).

Solution:​

Add the following to the [Peer] section of the client configuration file:

[Peer]
# Actively send a lightweight keepalive packet to the server every 25 seconds to maintain NAT hole punching
PersistentKeepalive = 25

(The peer.conf generated by LinuxServer.io by default usually includes this setting).
