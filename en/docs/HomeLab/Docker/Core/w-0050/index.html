Troubleshooting and Cleaning Guide for Sudden Docker Disk Space Spikes

1. Space Localization: What Is Eating Up the Hard Drive?​

When system alerts trigger or the disk is full, avoid blind cleaning and locate the spatial distribution first.

1.1 Docker Native Space Analysis​

Use Docker's built-in analysis tools to quickly pinpoint whether Images, Containers, Local Volumes, or Build Cache are taking up space:

# View Docker overall resource usage summary
docker system df

# View detailed usage breakdown for each item (including container IDs, image sizes, and volume sharing info)
docker system df -v

1.2 Linux System-Level Investigation (Hunting Hidden Bloated Files)​

The default Docker storage path is /var/lib/docker (the following operations usually require root or sudo privileges). If docker system df shows anomalies but fails to catch the culprit, it is usually standard output logs (*-json.log) accumulated under /var/lib/docker/containers/.

# Find the top 20 largest files or directories under /var/lib/docker (avoiding cross-filesystem scanning)
sudo du -ahx /var/lib/docker | sort -rh | head -n 20

# Specifically check the JSON Log sizes of all containers and sort by capacity (descending)
sudo find /var/lib/docker/containers/ -name "*-json.log" -exec du -h {} + | sort -rh | head -n 20

2. Emergency Response: Log File Bloat First Aid (Live Truncation)​

When you discover that a container's log reaches tens of GBs, never delete it directly using rm -f <container_id>-json.log!

Why can't you use rm? In the Linux kernel, as long as the Docker daemon (dockerd) still holds the file's File Descriptor (FD), even if the directory pointer is removed, the Inode remains in the (deleted) state and disk space will not be released until the Docker service is restarted.

Correct Cleanup Method: truncate​

Use the truncate command to reduce the file length to 0, which preserves the File Descriptor while immediately returning disk space:

# Syntax:
# sudo truncate -s 0 /var/lib/docker/containers/<CONTAINER_ID>/<CONTAINER_ID>-json.log

# Example: Clear a single container's log
sudo truncate -s 0 /var/lib/docker/containers/a1b2c3d4e5f6.../a1b2c3d4e5f6...-json.log

# Universal first-aid command: One-click zeroing of all Docker json-logs larger than 100M on the host
sudo find /var/lib/docker/containers/ -name "*-json.log" -size +100M -exec truncate -s 0 {} \;

3. Permanent Solution: Limiting Log Limits and Auto-Rotation (Log Rotation)​

Clearing is only for emergencies; without setting up Log Rotation, logs will eventually fill up the hard drive again. Restriction methods are divided into "global defaults" and "single project/container customization".

Option A: Global Configuration (/etc/docker/daemon.json) —— Highly Recommended​

Once configured, all subsequently created containers will inherit this limit rule.

  1. Edit /etc/docker/daemon.json:
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "50m",
    "max-file": "3"
  }
}
  • max-size: Triggers rotation when a single log file reaches this size (e.g., 50m or 100m).
  • max-file: Upper limit of rolling backup files retained. When exceeded, the oldest file is automatically overwritten. In this example, it uses a maximum of 50m * 3 = 150m.
  1. Reload settings and restart Docker service:
systemctl daemon-reload
systemctl restart docker
Updated 2026-11-27

There are three things to note regarding the reload commands above:

  1. systemctl daemon-reload is only used to reload systemd .service unit files; modifying /etc/docker/daemon.json does not require running this command.
  2. systemctl restart docker will interrupt and restart all running containers on the host (unless "live-restore": true is enabled beforehand). If you only need to apply daemon.json options supporting hot-reloading, you can run sudo systemctl reload docker first; however, whether using reload or restart, log-driver and log-opts will still only apply to newly created containers afterwards.
  3. If docker compose down was already executed in the example below, containers and networks have been removed, and executing docker compose up -d right after will rebuild them without needing an additional --force-recreate; if you want to rebuild containers in place without tearing down the network, run docker compose up -d --force-recreate directly.

Important Trap Reminder: Modifying daemon.json only takes effect for "newly created" containers after restart. Existing containers must be recreated to apply:

# Containers managed by traditional run:
docker stop <name> && docker rm <name> && docker run ...

# Containers managed by Docker Compose:
docker compose down && docker compose up -d

Option B: Compose Project Individual Configuration (compose.yaml)​

If certain applications (such as high-traffic Nginx, database synchronization services) require individual log quotas, you can declare them at the service level:

services:
  app-service:
    image: my-app:latest
    logging:
      driver: "json-file"
      options:
        max-size: "10m"
        max-file: "3"

Apply changes:

docker compose up -d --force-recreate

4. Space Reclaiming Command Encyclopedia (Prune Series)​

Before cleaning, make sure to clarify the impact scope of each level of cleanup commands to avoid accidentally deleting production data.

4.1 Container and Image Safe Cleanup​

# 1. Safe cleanup (Daily use)
# Deletes: All stopped containers, unused networks, dangling images (images without a tag like <none>)
docker system prune -f

# 2. Deep cleanup (Reclaiming large amounts of space)
# Deletes: All stopped containers, unused networks, and "all images not currently referenced by any container"
# Note: Re-opening applications will require pulling images again
docker system prune -a -f

# 3. Clean build cache
# Caches left behind during Dockerfile build, which often accumulate tens of GBs over years
docker builder prune -a -f

4.2 Volume Cleanup (Most Dangerous, Extreme Caution Required)​

By default, docker system prune does not proactively delete Volumes, because Volumes usually store databases or persistent data.

# List orphaned volumes (volumes not mounted by any container)
docker volume ls -f dangling=true

# Clear all orphaned volumes (Warning: If there are database containers out of maintenance but needed later, their data will be permanently lost!)
docker volume prune -f

# Ultimate cleanup (Sweeps up unmounted volumes as well; do not use lightly unless resetting the environment)
docker system prune -a --volumes -f

5. Automated Blast-Proofing Mechanism: Linux Logrotate System Backup​

If there are legacy containers in the environment that cannot easily be refactored to apply max-size, you can use the host system's logrotate to create scheduled backups.

Create /etc/logrotate.d/docker-containers (suggested precise match *-json.log):

/var/lib/docker/containers/*/*-json.log {
    rotate 3
    daily
    copytruncate
    compress
    missingok
    notifempty
    maxsize 100M
}
  • copytruncate: Very crucial. It copies the log file first and then truncates the original file to zero, without interrupting Docker's File Descriptor, equivalent to automating truncate.

Test if configuration is correct (no actual changes, requires sudo privileges):

sudo logrotate -d /etc/logrotate.d/docker-containers

6. Maintenance Quick Reference Logic Flow​

Disk Space Alert (100% Full)
  │
  ├─ 1. docker system df (Confirm whether it's Images/Build Cache or Container Logs)
  │     └─ If Build Cache ──> docker builder prune -f
  │     └─ If Dangling Images ──> docker image prune -f
  │
  ├─ 2. If Logs are Bloated (du -ahx /var/lib/docker | grep -i 'json\.log')
  │     └─ Immediate First Aid ──> truncate -s 0 <path_to_log>
  │     └─ Permanent Fix ──> Configure /etc/docker/daemon.json (max-size/max-file)
  │                          └─ Recreate containers to apply (docker compose down && docker compose up -d)
  │
  └─ 3. Regular Maintenance ──> Create cron schedule to run docker system prune -f
Updated 2026-11-27

The last line of point 2 in the flowchart (docker compose down && up -d) missed the command prefix; it should correctly be docker compose down && docker compose up -d (or use docker compose up -d --force-recreate); additionally, the . in grep -i json.log represents any character in regex, so precise matching is recommended as grep -i 'json\.log'.
